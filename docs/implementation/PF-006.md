| Field | Value |
|---|---|
| Story | PF-006 — Provision the local container runtime without Docker knowledge |
| Delivery status | Repository implementation complete |
| Release status | Requires approved third-party terms, signed vendor artifacts, platform signing/notarization authorities, and the no-skip pristine-host certification campaign |
| Parent workflow | PF-001 `EnsureContainerRuntime` phase |

| Persistent authority | Authenticated runtime operation, consent, ownership, artifact, privilege, reboot, and parent-install journals |
| User surface | Agent-host setup surface or embedded authenticated loopback setup UI |

PF-006 is the runtime sub-saga of the one-action PF-001 installation. A user installs the AgentMemory
MCP; the signed launcher discovers whether a safe local container runtime already exists and either
adopts it, starts it, installs the certified platform runtime, repairs only AgentMemory-owned state,
or blocks. The user is never required to know Docker terminology, choose a context, edit a file, run a
terminal command, install Compose, or start a service manually.

Repository delivery and release certification are intentionally distinct. The repository contains the
complete fail-closed implementation and local/hosted verification machinery. A distributable release
must still provide the real publisher-signed artifacts and terms approval, then execute the signed
pristine-host campaign described in the PF-001 certification record. Missing external evidence keeps
the operation NotReady; it does not activate a development fallback.

## Clean Architecture boundaries

PF-006 preserves dependency direction across five layers:

- `runtimeinstall` owns the closed phase/state/action vocabularies, immutable host/runtime facts,
  terms authority, deterministic plan policy, canonical plan codec, ownership aggregate, transition
  evidence, reboot binding, compensation binding, and completion invariants. It imports no OS,
  Docker, HTTP, filesystem, package-manager, or UI implementation.
- `runtimeinstallapp` owns ordered execution, optimistic repository updates, first-unverified-phase
  resume, cancellation settlement, expected-outcome mapping, and completion receipt construction. It
  depends only on one narrow port per phase or durable authority.
- `runtimecatalogapp` verifies the release-selected catalog cell and projects only the platform facts,
  artifacts, executable roles, publisher identities, terms, and closed operations authorized by it.
- `runtimeprovision` implements Linux and desktop host boundaries. Shared orchestration is separated
  from build-selected macOS, Windows, and Linux native probes, signature verifiers, protected stores,
  privilege transports, process executors, and package/application transactions.
- `installprogress`, `setupprogressapp`, `setuphttp`, `runtimeconsent`, `runtimeconsentjournal`,
  `rebootevidence`, `rebootfs`, `rebootlogin`, artifact acquisition, and runtime removal are focused
  adapters/use cases. None may widen the runtime plan.

The launcher composition root reconstructs these capabilities only after authenticating the parent
installation, signed active release, retained runtime catalog, host evidence, runtime observation,
protected operation state, and product-owned executable inventory. Constructors reject absent and
typed-nil capabilities. Platform-unavailable build variants fail closed.

## Signed catalog and deterministic planning

The release contains a canonical signed runtime catalog rather than a mutable URL or version lookup.
The selected platform cell binds:

- platform, edition/distribution, OS/build range, architecture, resource and virtualization floors,
  support expiry, and anti-rollback sequence;
- exact Docker Engine/Desktop, CLI, Compose, containerd, Buildx, rootless, WSL, or distribution
  versions required by that cell;
- HTTPS origin/path policy, byte length, SHA-256, redistribution policy, repository metadata, package
  identity, native verification mechanism, publisher/key/certificate identity, and independently
  embedded publisher-key digest;
- closed installer executable role and argv template, prerequisite graph, allowed reboot exit codes,
  service/application identity, and capability-probe policy;
- terms ID, version, HTTPS URL, digest, presentation owner, and whether AgentMemory may present the
  terms before passing the vendor's documented acceptance flag; and
- download, expanded, reserve, proxy, rollback, created-component, and setting policy.

Outer release-resource verification and inner catalog-signature verification are separate gates. The
runtime-catalog signer cannot authorize native publishers, and the catalog cannot extend the embedded
publisher allowlist. Catalog sequence is protected by an authenticated anti-rollback anchor. The
retained object is reopened by descriptor, size, and digest before every trust-sensitive transition.

`RuntimeInstallPlanPolicy` accepts independently observed host and runtime evidence plus one verified
catalog projection. It returns exactly one closed action:

| Action | Preconditions | Permitted mutation |
|---|---|---|
| `AdoptCompatible` | Proven local running runtime passes the complete compatibility policy | None |
| `StartCompatible` | Proven local stopped runtime is otherwise compatible | Start only the recorded runtime |
| `InstallCertified` | No compatible runtime and the certified host/catalog cell matches | Exact catalog-authorized installation |
| `RepairManaged` | Authenticated ownership proves an incomplete AgentMemory-managed runtime | Only recorded owned components |
| `Block` | Remote/cloud/unsafe/conflicting/unsupported/ambiguous/insufficient state | None |

A binary name, PATH result, version string, environment-selected endpoint, context name, or responsive
daemon alone is insufficient. Discovery proves exact local endpoint, executable/package publisher,
Engine/Compose compatibility, Linux-container mode, security mode, read-only bind, named volume,
internal network, loopback publish, architecture, resource floor, and unrelated workload inventory.
External runtimes are addressed explicitly without changing global context, proxy, registry, resource,
update, Kubernetes, cloud/offload, image, container, network, volume, or user configuration.

## Durable runtime saga

The child aggregate executes these ordered transitions:

`DetectHost -> DetectRuntime -> PlanRuntime -> AwaitRuntimeConsent -> AcquireRuntime ->`
`VerifyRuntimeArtifact -> InstallPrerequisites -> InstallRuntime -> AwaitThirdPartyTerms ->`
`StartRuntime -> VerifyRuntimeCapabilities`.

Every transition has a durable before record and authenticated output. Evidence binds operation ID,
aggregate version, phase, attempt, plan and catalog digests, input/output digest, artifact digest,
ownership boundary, compensation authority, principal, machine, and previous record. A process, power,
network, or host interruption resumes at the first transition without verified output and re-probes
all external facts used by earlier evidence.

The first host mutation is unreachable until a prepared `RuntimeOwnershipRecord` is durable. The
record starts with the planned disposition and before-state hashes, then monotonically accumulates
artifacts, packages/applications, settings, privilege receipts, continuations, capability evidence,
and the final endpoint. Exactly one finalized ownership projection is returned to PF-001.

Closed terminal/pause outcomes are:

- `Cancelled` for explicit terms, elevation, restart, or setup cancellation;
- `PausedForAdministrator` for device policy, unavailable certified native authorization, or required
  organization-admin action;
- `UnsupportedHost` for uncertified OS/architecture/resources or unavailable virtualization;
- `RuntimeConflict` for unsafe or unrelated-workload conflicts;
- `FailedRecoverable` for a retryable dependency/transition failure;
- `RebootPending` only with a durable one-use continuation; and
- `Ready` only after every phase and capability receipt validates.

Private process/package/runtime diagnostics are mapped to typed content-free errors. Cancellation after
the ownership boundary cannot finish until exact compensation is durably settled or left explicitly
recoverable.

## Consent and novice setup experience

The plan shown to the user is the same canonical plan executed later. It describes the selected
runtime, official source and publisher, download and disk sizes, packages/features/settings, privilege
scope, terms identity and URL, restart possibility, ownership result, rollback limits, and exactly one
safe next action. The decision is never preselected.

A consent receipt binds the current OS principal, operation, plan digest, terms digest, decision,
issued time, expiry, and purpose-separated signature. It is journaled in an owner-protected store and
verified again before mutation. Plan, publisher, permission, terms, principal, or operation drift
requires a new decision. AgentMemory neither asks the user for employer size/revenue nor records an
eligibility conclusion. It cannot accept Docker Desktop terms automatically; `--accept-license` is
allowed only after the exact AgentMemory-presented terms receipt is authenticated.

The embedded setup UI is generated into the signed launcher and uses no remote script, font, image,
analytics, or network dependency. A random one-use IPv4/IPv6 loopback capability begins in the URL
fragment, is removed from browser history, and is exchanged for an authorization header plus CSRF
token. The server binds Host, Origin, Fetch Metadata, principal, operation, plan, expiry, request size,
rate, and sequence; decisions are replay-safe and progress streams over authenticated SSE. Terminal
state closes the server. Keyboard, screen-reader, reduced-motion, contrast, zoom, error, and localized
message-key behavior are release-gated.

## Acquisition, trust, and privilege

Acquisition is unprivileged, content-addressed, capacity-reserved, proxy-aware, resumable by verified
range, and bounded by signed source policy. Redirects are revalidated; PAC/proxy credentials remain in
the OS credential flow; partial or final bytes are never promoted without exact chunk/final evidence.
Offline runtime artifacts are accepted only when redistribution is authorized or the user supplies the
exact official artifact independently; all digest and publisher gates remain identical.

Privilege is a closed typed protocol, never a command runner. Linux supports fixed operations for
repository/key publication, exact package closure, subordinate IDs, rootless service state, and owned
removal. Desktop supports fixed verified package/application/prerequisite transactions. Requests are
canonical bounded stdin and bind the retained release, catalog, plan, helper identity, artifact,
principal/machine, operation state, nonce, expiry, expected state, and replay identity. No shell,
password, arbitrary executable, URL, argv extension, environment map, working directory, or mutable
PATH crosses the broker.

The immutable helper independently verifies its signed executable, caller UID/SID, parent process,
plan/catalog/release bytes, artifact descriptor, native publisher, nonce, expiry, replay journal, and
current state before selecting one transaction. It uses a global operation lock, protected
machine-local receipt key, pending/completed journal, deterministic postcondition, and signed/HMAC
receipt. User denial, policy denial, malformed receipt, and TOCTOU substitution have distinct closed
outcomes without leaking private diagnostics.

## Platform behavior

### macOS

The Darwin composition selects the architecture-correct signed Docker Desktop cell, verifies digest,
Developer ID, notarization, mounted-image identity, application bundle identity, helper identity, and
all filesystem ownership/mode/link invariants. Installation uses the catalog-fixed mounted installer
with `--accept-license` and the exact `--user=<principal>` only after consent. It avoids drag/drop,
PATH edits, onboarding, account sign-in, and settings navigation. The native launcher then starts the
exact application and proves the Docker/Compose capability contract. A no-CGO build cannot claim this
native authority.

### Windows

The Windows composition certifies Windows 11 x86-64 and the WSL2/Linux-container backend only. Docker
Desktop uses the documented per-user installation with `install --user --quiet --accept-license
--backend=wsl-2 --no-windows-containers`; it never uses `--always-run-service` or adds `docker-users`.
The installer and every Microsoft WSL prerequisite are digest-bound and verified through
`WinVerifyTrust` plus exact leaf-certificate digest. The fixed prerequisite graph probes edition,
build, SLAT/firmware, features, WSL version, and distribution inventory, and cannot mutate an existing
distribution. Required feature/MSI operations use UAC through the signed helper and suppress automatic
restart until a continuation is durable.

### Linux

Only signed Debian/Ubuntu and Fedora-family catalog cells are eligible. APT and DNF repository
metadata, pinned keys, package manifests, architecture, version, size, digest, and native package
signatures are verified before a typed package transaction installs the exact Docker Engine/CLI,
containerd, Buildx, Compose, and rootless packages. Repository and package trust are verified
independently.

The invoking non-root principal receives collision-checked ranges of at least 65,536 subordinate UIDs
and GIDs. The package-owned rootless setup tool, exact user systemd unit, linger state, context, and
local socket are established and re-proved. Final evidence requires rootless security options. PF-006
never disables an existing rootful daemon, passes `--force`, starts a new rootful daemon, or adds the
user to a Docker group; an unsafe conflict blocks.

These policies remain aligned with the current official Docker guidance for
[macOS command-line installation](https://docs.docker.com/desktop/setup/install/mac-install/),
[Windows per-user/WSL2 installation](https://docs.docker.com/desktop/setup/install/windows-install/),
[Docker Desktop licensing](https://docs.docker.com/subscription/desktop-license/),
[Linux rootless prerequisites](https://docs.docker.com/engine/security/rootless/), and
[Microsoft WSL installation/restart behavior](https://learn.microsoft.com/en-us/windows/wsl/install).
Exact supported cells still come only from a reviewed signed release catalog.

## Reboot continuation

Before an approved reboot or logout, PF-006 flushes the operation journal and stores an owner-only
one-use continuation containing only launcher path/hash, operation ID, journal path/hash, next phase,
expiry, and a random non-secret nonce. Platform login registration is per-user. Resume authenticates
the binary, journal, owner, machine, principal, operation, phase, expiry, and nonce, atomically consumes
the nonce before executing, and removes the registration on success, cancellation, expiry, or terminal
failure. It carries no credential, provider secret, Docker token, Brain data, or arbitrary command.

## Capabilities, ownership, and removal

Runtime readiness is not inferred from process state. The probe creates and compensates exact signed
test resources to prove Engine API, Compose, Linux architecture, read-only bind enforcement, named
volume persistence, internal network behavior, loopback-only publishing, security mode, and workload
inventory. Every temporary object has a signed identity and must be removed even when an intermediate
probe fails.

Uninstalling AgentMemory preserves Docker, WSL, existing distributions, and every non-AgentMemory
resource. Runtime removal is a separate use case with a new impact plan and confirmation. It requires
`ProvisionedByAgentMemory`, exact finalized ownership, current publisher/runtime identity, and an
exhaustive inventory proving no foreign container, image, volume, network, context, Compose project,
client, package, service, or setting dependency. Absence or uncertainty preserves the runtime.
