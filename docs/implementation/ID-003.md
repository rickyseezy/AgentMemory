ID-003 represents repository topology as evidence-backed links between stable Project and Repository
identities. Discovery never merges identities and never mutates canonical state. It produces candidate
`CONTAINS_REPOSITORY`, `SUBMODULE_OF`, `FORK_OF`, and `PROJECT_USES_REPOSITORY` assertions. A candidate
becomes canonical only through `ConfirmRepositoryLinkCommand` using deterministic evidence of the
declared class or explicit owner confirmation.

## Clean Architecture ownership

- `identity.domain.topology` owns endpoint/relation/evidence enums, the candidate confirmation policy,
  validity, aggregate versions, correction history, and canonical events.
- `DiscoverRepositoryTopologyHandler` authorizes the Brain, validates active endpoint ownership, and
  deterministically coalesces duplicate parser evidence. It has no framework or database dependency.
- `ConfirmRepositoryLinkHandler` owns request-digest idempotency, duplicate-effective-state rejection,
  optimistic correction, UUIDv7 allocation, and the transactional command boundary.
- `GitCliRepositoryTopologyAdapter` owns bounded host parsing. It invokes one absolute Git executable
  with argv only, does not use a shell, does not follow symlinks, enforces traversal/output/count/size
  bounds, and returns only installation-keyed fingerprints and stable IDs.
- `SqliteRepositoryLinkUnitOfWork` owns serialized current-grant authorization, endpoint validation,
  compare-and-swap persistence, the canonical domain event, append-only history, and the current
  `project_repositories` read projection in one transaction.
- The composition root supplies every concrete capability. Domain and application modules remain
  independent of FastAPI, Pydantic, SQLAlchemy, Git subprocesses, and other bounded contexts.

## Topology and identity policy

### Nested repositories and submodules

Every detected Git worktree or bare repository is a separate discovered node. A nested `.git`
directory or file creates a candidate parent `CONTAINS_REPOSITORY` child link; it never reuses the
parent Repository ID. A declared submodule becomes child `SUBMODULE_OF` parent only when the strict
`.gitmodules` path resolves inside its parent and Git's index contains the matching `160000` gitlink.
The candidate then carries both declaration and gitlink evidence.

### Forks and clones

The parser never derives repository identity from names, working-tree content, or remote resemblance.
It proposes `FORK_OF` only when independent Git histories expose the same root set but their canonical
Repository fingerprints differ. An explicit `upstream` remote that matches the other repository gives
deterministic direction; otherwise direction remains candidate-strength and requires owner
confirmation. Confirming a fork link connects two existing, distinct Repository IDs—it never merges
or aliases them. Unrelated repositories with identical files or a similar remote produce no fork link.

### Monorepos

Each strict `.agentmemory/project.json` identifies one logical Project and Repository. Component roots
are normalized, containment-checked, canonicalized as a set, and immediately HMAC-indexed. The raw
root names are not stored or returned. Multiple Projects may link to the same Repository with distinct
component-scope fingerprints, so retrieval can later authorize one package without implicitly
authorizing every package in the monorepo.

### Non-Git and bare repositories

An explicit manifest containing both UUIDv7 Project and Repository identities is the only portable
non-Git topology authority. Tree similarity never creates a non-Git Repository link. Empty bare Git
repositories are supported when they have an explicit Repository identity; nonportable empty Git
nodes remain unresolved candidates and cannot be confirmed until identity resolution assigns them a
Repository.

## Canonical persistence and corrections

`repository_topology_links` stores the active aggregate snapshot with Brain, typed endpoints,
relation, optional component-scope fingerprint, validity, status, and optimistic version. A partial
unique index prevents two active effective links for the same endpoint pair.

`repository_topology_link_history` stores every version's operation ID, request digest, event ID,
relation, component scope, canonical evidence, actor, grant, confirmation source, reason, and effective
time. Database triggers reject updates and deletes. The matching `RepositoryLinkConfirmed` or
`RepositoryLinkCorrected` event is appended to `domain_events` in the same transaction. Corrections
must retain Brain and endpoint identities, provide the exact current version and a closed-format reason,
and have an effective time later than the prior version. A relationship-type or scope correction
therefore never destroys its previous meaning or provenance.

`project_repositories` is a current read projection for ID-001 resolution. Confirming a
`PROJECT_USES_REPOSITORY` aggregate upserts that projection transactionally as `primary` or
`component`. Repository-to-repository links remain canonical events and relational aggregate state;
later graph projection stories derive Neo4j state rather than making Neo4j a second write authority.

Migration downgrade is allowed only before canonical ID-003 links exist. Once links exist, downgrade
fails closed instead of deleting their aggregate history or domain events.

## API and privacy

Both endpoints authenticate the local launcher capability before application authorization. Discovery
accepts only stable IDs, closed relation/evidence values, and keyed digests; no request field accepts a
host path or remote URL. Confirmation additionally requires `Idempotency-Key` to equal `operation_id`.
All authorization, validation, conflict, and dependency failures use bounded problem details without
raw filesystem, Git, SQL, exception, or repository-content data.

The host adapter keeps raw paths ephemeral and excludes them from public values and repr output. Local
path remotes are deliberately ignored rather than fingerprinted. Network remotes pass the existing
credential-stripping canonicalizer before HMAC. Symlinks are not followed during discovery, component
and submodule roots cannot escape their Repository, and all enumeration is bounded.
