# ADP-003 implementation record

| Field | Value |
|---|---|
| Story | ADP-003 — Declare host capabilities honestly |
| Delivery status | Repository implementation complete |
| Declaration authority | Immutable `AdapterCapabilityManifest` per adapter ID/version |
| Runtime authority | Latest append-only `AdapterCapabilityObservation` |
| Relational schema | `0008_adp003_adapter_capabilities` |
| Operator display | Authenticated capability matrix command/query API |
| Event binding | Adapter ID/version/binary digest, manifest digest, and capture method on every encrypted event envelope |

ADP-003 makes missing telemetry an explicit domain fact. Every adapter version declares a complete
matrix containing exactly one status for every closed `CaptureCapability`: `native`, `inferred`,
`explicit_tool_only`, `unsupported`, or `permission_denied`. Policies consume
`EvidenceAvailability`; no domain or application component branches on Codex, Claude, Gemini, GLM,
or another host name.

## Architecture and invariants

The implementation follows the ingestion bounded context's Clean Architecture layers:

- `ingestion.domain.adapter_capability` owns the immutable manifest, effective observation,
  registration aggregate, status transitions, compatibility impacts, and authorization policy.
- `ingestion.domain.ports` defines separate command repository/Unit of Work and read projection
  contracts. It does not expose SQL or a generic persistence service.
- `ingestion.application.adapter_capabilities` implements `RegisterAgentAdapterCommand`,
  `ObserveAdapterCapabilitiesCommand`, and capability query handlers.
- `sqlite_capabilities` is the only relational implementation. It persists manifests,
  observations, warnings, exact idempotency receipts, and hash-chained audit facts atomically.
- `capability_http_api` is a strict authenticated adapter. It converts transport values to closed
  domain enums, requires an exact `Idempotency-Key`, and returns content-free operator views.

An adapter ID/version identifies exactly one canonical manifest digest. Re-registering that version
with different binary, family, schema, or status evidence fails with `AM_CONFLICT`. An exact retry
returns `duplicate`; a new operation with unchanged effective state returns `unchanged` without
creating another observation. Operations are bound to a SHA-256 of the complete command, so an
operation ID cannot be reused with changed input.

Every manifest contains the complete closed capability set. Duplicate/missing signals, invalid
identity tokens, unsupported schema majors, and a supported event family whose required evidence is
not observable fail before persistence. A runtime observation may retain the declared status or turn
an observable signal into `permission_denied`; it cannot promote an unsupported signal or change the
declared capture method. Permission restoration returns to the exact declared method.

## Versioned compatibility and downstream enforcement

Initial registration creates revision 1. Permission loss/restoration appends a new revision while the
manifest remains immutable. A new adapter version compares its effective matrix with the latest
registered version. Every changed capability creates a typed warning:

| Transition | Warning | Impact |
|---|---|---|
| observable to permission denied | `permission_lost` | breaking |
| permission denied to declared observable method | `permission_restored` | informational |
| observable to unavailable | `signal_removed` | breaking |
| unavailable to observable | `signal_added` | informational |
| native/inferred/explicit-tool-only change | `capture_method_changed` | informational or degraded according to evidence strength |

`AgentEventAdmissionHandler` loads the exact registered adapter ID, version, and binary digest. It
requires the event's manifest digest to match the immutable manifest and authorizes only when the
current `EvidenceAvailability` for the event family's required capability is observable with the
event's exact capture method. Permission loss therefore stops affected capture immediately;
unsupported evidence is never interpreted as a negative observation.

Accepted event envelopes store searchable adapter ID/version, binary digest, capability-manifest
digest, and capture method beside the encrypted payload. This preserves evidence lineage without
decrypting user content and allows future query and learning policies to exclude weak or unavailable
signals using the status model.

## Persistence and operator API

Migration `0008_adp003_adapter_capabilities` adds:

- a manifest-format discriminator and immutable adapter ID/version uniqueness;
- append-only capability observations with monotonic per-version revisions;
- version-scoped compatibility warnings;
- exact command/idempotency receipts;
- indexed capability provenance on `agent_event_envelopes`.

The migration downgrade succeeds only before capability evidence exists. It fails closed rather than
delete manifests, observations, warnings, command receipts, or bound event evidence.

The authenticated loopback contract exposes:

- `POST /v1/agent-adapters:register`;
- `POST /v1/agent-adapters/{adapter_id}/versions/{adapter_version}:observe`;
- `GET /v1/agent-adapters/capabilities`;
- `GET /v1/agent-adapters/{adapter_id}/versions/{adapter_version}/capabilities`.

The query responses are the operator-facing display contract. They show every capability—including
unsupported and permission-denied entries—the immutable digest, current revision/time, supported
families, and bounded compatibility warnings. They never expose prompts, paths, payloads, credentials,
or arbitrary exception text. The same routes are part of deterministic Core OpenAPI export so later
CLI and UI packages consume one normative contract.
