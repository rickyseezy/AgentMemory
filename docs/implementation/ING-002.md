## Outcome

ING-002 makes every retry-sensitive boundary prove identity before it performs an effective side
effect. Canonical capture already uses event identity and ordering uniqueness; this story adds a
persistent consumer inbox, projection receipts, command receipts, provider-operation reservations,
semantic provider result caching, request/result digests for jobs, and a common conflict-evidence
ledger. The live canonical-event consumer claims its inbox receipt before verification and commits
the inbox result, terminal projection, source outbox completion, and audit outcome in one serialized
SQLite transaction.

An exact repeat either waits for the current lease or replays the committed result. A caller that
reuses the same identity for different content is never treated as a duplicate: the operation fails
closed, its effective state is not replaced, and one content-free hash-chained conflict audit record
is committed independently of the rejected transaction.

Potentially billable provider work is protected twice. The local reservation serializes concurrent
callers and caches a content-addressed result. Every actual provider invocation receives the stable
`am-provider-v1:<semantic-cache-digest>` downstream idempotency key, so recovery after an uncertain
response repeats the same provider identity rather than creating a second charge. A provider adapter
must preserve this key unchanged; adapters that cannot provide that contract cannot implement the
billable backend port.

## Clean Architecture and SOLID boundaries

- `ingestion.domain.durable_processing` owns the inbox claim/replay/wait states and validates their
  exact evidence shapes without importing SQL, crypto, frameworks, or another bounded context.
- `ingestion.application.durable_processing` claims the source outbox message, then the consumer
  inbox, and only then invokes the canonical verifier. Replay and contention paths execute no
  projection side effect.
- `DurableEventProcessingRepository` exposes the minimum claim, complete, replay, repair, retry, and
  recovery capabilities. `SqliteDurableEventProcessingRepository` implements those capabilities
  behind short FULL-synchronous transactions and the Core single-writer policy.
- `providers.domain.idempotency` owns provider purposes, privacy classes, complete semantic identity,
  claims, outcomes, and execution results. It has no vendor or persistence dependency.
- `ExecuteProviderOperationHandler` depends only on `ProviderOperationCache`,
  `BillableProviderBackend`, and `Clock` ports. The SQLite cache and every provider vendor adapter are
  replaceable without changing the use case.
- `SqliteProviderOperationCache` is solely responsible for persistent claim arbitration, compare-and-
  set completion, lease recovery, semantic replay, and conflict audit persistence.
- Event capture conflict reporting is orchestrated by `AppendAgentEventHandler`: the rejected event
  transaction rolls back first, then a fresh Unit of Work records the conflict. Repository methods do
  not commit themselves.

These boundaries preserve Single Responsibility, Dependency Inversion, Interface Segregation, and
Open/Closed provider extensibility. The import-linter contracts enforce domain/application direction
rather than relying on convention.

## Idempotency identities

Each identity has both a physical uniqueness constraint and a content digest capable of detecting
identity reuse:

| Boundary | Unique identity | Bound content/evidence |
|---|---|---|
| Canonical event | event ID; ordering key plus sequence | canonical event/content digest |
| Command | command name plus caller idempotency key | request and result SHA-256 |
| Consumer inbox | consumer plus message ID; consumer plus effective event key | source payload SHA-256 and committed result SHA-256 |
| Job | job kind plus idempotency key | request SHA-256, optional input reference, terminal result SHA-256 |
| Provider operation | profile plus caller key; globally unique operation ID | caller request SHA-256 |
| Provider semantic result | Brain-scoped semantic cache SHA-256 | profile/model revision, ordered content hashes, purpose, preprocessing revision, and privacy class |
| Projection | projection plus effective key; projection plus source message plus generation | request and result SHA-256 |

The semantic provider key includes Brain identity to prevent reuse across authorization domains. The
ordered content digest tuple is retained because changing input order can change embeddings,
reranking, extraction, billing, or result interpretation. Model revision accepts only immutable
40/64-character hexadecimal revisions, never a mutable model alias.

## Consumer transaction and recovery semantics

The live consumer follows this closed path:

1. claim one ready source outbox row under its dispatcher lease;
2. atomically insert, wait on, reclaim, or replay the consumer inbox identity;
3. execute canonical verification only for a `claimed` inbox;
4. in one transaction, insert the terminal event projection and projection idempotency receipt,
   complete the exact source outbox lease, complete the exact inbox lease, and append one projection
   audit fact; and
5. return completion only after that transaction commits.

A crash before step 4 leaves no effective projection and both leases eventually become reclaimable.
A crash after step 4 but before transport acknowledgement redelivers into `replay`; exact inbox and
projection result digests are revalidated, the repeated source lease is completed, and no second
projection or audit outcome is created. A conflicting payload digest terminates the inbox and source
message as `repair_required`, opens one repair alert, and appends one deduplicated conflict fact.

All operations use compare-and-set predicates containing the current state and lease owner. A stale
worker therefore cannot complete, retry, or repair work reclaimed by another worker.

## Provider transaction and billing semantics

`ProviderOperationRequest.cache_key_sha256` is canonical JSON over every semantic dimension.
`request_sha256` additionally binds the caller operation ID. Claim arbitration behaves as follows:

- no exact or semantic row: insert one processing reservation and return `claimed`;
- exact identity with another request digest: commit deduplicated conflict evidence and reject;
- active processing reservation: return `wait` without calling the backend;
- expired/due processing reservation: compare-and-set a new owner and increment attempts;
- completed exact or semantic reservation: return its content-addressed outcome as `cached`.

Completion succeeds only for the current owner and stores an exact `cas://sha256/<digest>` reference
plus nonnegative usage. Dependency failure keeps the same semantic identity, records a bounded retry
code/time, and releases the reservation for later reclaim. If the process dies after the provider
responds but before local completion, the later worker invokes the provider with the identical
downstream key; a conforming provider returns the original billable operation rather than charging
again.

## Relational migration and downgrade policy

Migration `0010_ing002_idempotent_delivery` creates `idempotency_conflicts`, `command_receipts`,
`inbox_receipts`, `provider_operation_results`, and `projection_idempotency_receipts`. It extends jobs
with input reference, request/result digests, and completion time. Digest lengths, closed states,
lease/result state shapes, attempts, foreign keys, and every required uniqueness boundary are
database constraints, so an alternate adapter or process cannot silently bypass them.

Legacy job request digests are deterministically backfilled from separator-bound job kind and idempotency key
before the column becomes mandatory. A pre-ING-002 `succeeded` job receives an explicitly namespaced,
opaque legacy-success digest bound to that immutable identity and its existing update time; it preserves
the historical terminal state without claiming a reconstructable provider output. Downgrade is refused
while any ING-002 receipt, provider result, or conflict evidence exists; deleting such evidence during
rollback would make a later retry unsafe.

## Privacy and audit

Conflict rows and audit facts contain UUIDs or one-way identity/request hashes, closed namespace and
action values, Brain/actor identity, timestamps, and before/after digests. They contain no event body,
prompt, provider input/output, embedding, path, arbitrary exception, or credential. Repeating the
same conflict does not create another audit outcome.
