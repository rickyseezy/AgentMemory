| Field | Value |
|---|---|
| Story | PF-001 — Install the complete local Brain from one MCP installation |
| Delivery status | In progress |
| Release status | Not releasable; all missing production capabilities fail closed |

PF-001 is release-complete only when every acceptance criterion and mandatory test in
`TECHNICAL_REQUIREMENTS.md` is executable and passing against production artifacts on every
certified host. Passing unit tests for ports or policy does not prove that Docker, the Brain,
Neo4j, SQLite, models, or an agent integration can actually be installed.

This increment deliberately has no fake composition root and no adapter that can report Ready
from process existence, a filename, a Docker binary on `PATH`, or mocked service health. Missing
production inputs therefore keep the story in progress.

## Current release-completion delta

The implementation has advanced beyond several historical gap descriptions retained below. The
current shared tree now includes the runnable local Core, SQLite migrations, Neo4j integration,
three llama.cpp provider roles, hardened container images, protected secret projection, concrete
Core readiness/activation clients, native launcher factory, setup UI, supported agent document
formats, Windows Job Object execution, release-evidence verifiers, and an authenticated minimal
Ready MCP surface. The default Qwen embedding, reranking, and extraction artifacts are locked to
official revisions and exact digests. Release qualification downloads every source again, converts
the reranker twice with a digest-pinned network-disabled converter, compares both outputs, and live
tests all three roles in network-disabled containers.

PF-001 is still not release-complete for a pristine nontechnical user. The remaining repository-
owned critical path is:

1. wire the protected pristine-start preparation repository, native host binder, retained signed
   distribution catalog, canonical plan/operation/pointer publication, and complete fourteen-phase
   `InstallApplication` lifecycle into the production `NewFirstStartFactory` composition;
2. bind setup Accept/Retry decisions to that exact idempotent installer/resume authority (Cancel
   and Decline already persist cancellation intent);
3. assemble and publish the immutable multi-platform release, signed Compose lock, model payloads,
   SBOMs, provenance, Sigstore offline bundles, native installers/helpers, and complete offline
   bundle consumed by the initializer; and
4. execute the clean-host certification matrix and attach its evidence to the exact release
   commit/artifacts.

External release inputs remain separate blockers: Apple Developer ID/notarization authority,
Windows Authenticode authority, hardware-backed or approved release signing identity, runtime-vendor
terms and redistribution approvals, and the required pristine native hosts. Repository code and CI
must fail closed when any of those inputs are absent; tests cannot manufacture them.

## Delivered in this increment

### Installation kernel and recovery

- A closed fourteen-phase `InstallApplication` saga implements VerifyHost through
  CommitActiveRelease with one narrow capability per phase.
- The aggregate binds operation ID, canonical plan digest, phase, attempt, verified artifacts,
  non-secret facts, runtime ownership, compensation boundary, next action, and reboot receipt.
- Save-before-side-effect and save-after-transition rules make the first unverified phase the
  only retry point. Re-entry validates the same plan and returns `AlreadyReady` only from a
  fully restored Ready aggregate.
- A cross-process host lock, versioned operation repository, HMAC-chained journal, and protected
  monotonic rollback anchor reject tamper, replay, plan substitution, skipped phases, duplicate
  completion, and ambiguous crash states.
- Active cancellation is a plan-bound mutation in the same authenticated operation aggregate and
  compare-and-swap authority as phase progress. `Cancel` does not wait for the machine mutation
  lock or claim terminal settlement; the running installer watches durable intent, cancels the
  phase context, persists `Cancelled`, performs owned cleanup with a fresh bounded context, and
  only then acknowledges the request. The short operation-state fence makes cancellation versus
  Ready a single linearizable decision across processes.
- Public application and phase errors use closed, privacy-safe codes; raw command output, paths,
  credentials, and platform diagnostics do not enter persisted step evidence.

### Platform-protected bootstrap state

- Pristine start now writes a purpose-separated rollback-protected preparation intent before a
  plan, operation, or pointer can be published. It retains the exact verified template digest,
  operation/installation/generation/Brain/owner/agent-entry UUIDv7 identities, security epoch, and
  confirmed derived-plan digest. Concurrent launches select one winner; crashes and launcher
  restarts replay that exact authority instead of regenerating identities or falling forward to a
  newer template.
- The first-start template adapter rechecks template kind, execution purpose, media type, platform,
  byte length, and digest and resolves durable preparations by exact digest without falling
  forward. The native composition now creates a fourth purpose-separated protected journal,
  resolves the invoking owner's certified agent configuration location, binds the native Docker
  endpoint and current launcher digest, and derives only the permitted per-host plan fields. A full
  canonical plan cannot be listed inside the signed release manifest that it embeds: doing so would
  create an impossible SHA-256 self-reference. Therefore the production source must be a separate
  signed bootstrap catalog binding both the release-manifest digest and template digest. The
  descriptor-rooted retained loader, signed outer-catalog verifier, inner product-manifest
  verifier, exact-digest replay, and no-fall-forward template source are now implemented. The
  production factory still needs its public release trust material and phase composition before
  first start can publish.

- Linux uses owner-bound, no-symlink, regular-file paths, `0600` key material, atomic
  replacement, file/directory synchronization, and anchored replay protection.
- macOS binds the invoking user and device, rejects nontrivial ACLs, walks controlled paths
  without following symlinks, uses the Data Protection Keychain boundary for operation keys,
  and uses `F_FULLFSYNC`. A no-cgo build fails closed.
- Windows binds MachineGuid plus the invoking token SID. A random 256-bit operation key is
  user-DPAPI protected inside a non-roaming Credential Manager generic credential. Protected
  DACLs, owner-only mutexes, no-delete-share descriptor guards, no-reparse walks, hard-link/ADS/
  foreign-owner rejection, `ReplaceFileW` or write-through `MoveFileExW`, identity recheck, and
  `FlushFileBuffers` protect journal and anchor publication.
- Raw operation IDs never become filesystem components or Windows credential target names;
  fixed digest-encoded locators are used instead.

### Runtime policy and parent-phase integration

- The PF-006 runtime aggregate, exact runtime install plan, signed canonical runtime catalog,
  consent/terms bindings, prerequisite graph, ownership disposition, reboot receipt, and
  completion receipt are implemented as domain/application contracts.
- Runtime identifiers, versions, source authorities, digests, publishers, host tuples, and
  prerequisite manifests use closed validation and canonical encoding.
- `EnsureContainerRuntime` binds the nested signed runtime plan to the parent PF-001 plan,
  accepts only aggregate-authenticated outcomes, carries a one-use verified reboot receipt,
  and maps administrator, cancellation, unsupported-host, conflict, retry, and completion
  states without manufacturing capabilities or ownership.
- The PF-006 aggregate now has a production authenticated repository with a purpose-separated
  protected journal and cross-process state fence. It strictly decodes canonical snapshots,
  restores the complete transition history, applies aggregate-version compare-and-swap, confirms
  durability on exact replay, and rejects stale, divergent, substituted, or malformed state.
- Certified macOS and Windows Docker Desktop execution now has a complete fail-closed application
  boundary: signed immutable desktop/helper authorities; native host, resource, filesystem, at-rest
  encryption, WSL-feature, and version evidence; exact retained installer verification; installed
  application publisher/version verification; direct signed Docker and Compose inspection; explicit
  consent and authenticated helper request/receipt contracts; native macOS Authorization Services
  and Windows UAC helper invocation; application launch; reboot semantics; workload preservation;
  and an active Engine/Compose/bind/network/volume/loopback/local-execution probe with compensated
  cleanup. macOS uses Gatekeeper, Security.framework, notarization, signed Info.plist evidence, and
  owner-only no-follow workspaces. Windows uses BitLocker native evidence, WinVerifyTrust, exact
  external signer identity, fixed file-version evidence, protected DACL workspaces, DISM/WSL
  prerequisite evidence, and exact non-Windows-container installation policy.
- These adapters are not yet a production composition root. Signed runtime-to-desktop authority
  projection, the visible consent UI and its authenticated repository, production artifact
  acquisition, published signed native helper binaries, Windows WSL package acquisition on a
  pristine host, reboot/login continuation, release credentials, and clean-host certification
  remain explicit blockers. Windows process creation is now atomically assigned to its Job Object;
  unsupported or incomplete composition continues to fail closed and cannot report Ready.

  provider/model roles, Compose topology, compatibility ranges, trust policy, SBOM and

  monotonic release sequence.
- The release verifier requires signature, offline trust evidence, target/platform selection,

- Concrete Ed25519 and certificate-transparency signature verification, offline Sigstore/Rekor/

  signed qualification, OCI-index, native-publisher, and rollback-anchor adapters are present.
  The native release-trust stack now composes all of these gates with the retained signed
  distribution catalog and verified template source. Production public trust material, a concrete
  native-resource publisher verifier, anti-rollback anchor wiring, and final factory composition
  remain release blockers below.
- The top-level VerifyRelease phase advances only when the verified release identity, manifest
  digest, and sequence exactly equal the authenticated parent-plan projection.

### Artifact reservation and acquisition

- A signed artifact plan binds exact sources, chunks, offsets, sizes, digests, totals, rollback
  headroom, safety headroom, and content-addressed final keys.
- CAS storage accepts only descriptor-proven local filesystems: ext/XFS/Btrfs backed by a proven
  non-removable local block device on Linux, and `MNT_LOCAL` APFS/HFS on macOS. Reservation is
  narrower: only proven local ext/XFS currently qualifies. Btrfs is rejected because snapshots
  can invalidate NOCOW/preallocation guarantees, every Darwin filesystem including APFS/HFS is
  rejected until a snapshot-excluded dedicated allocation target can be proven, and Windows
  artifact reservation remains unsupported. Ambiguous backing storage always fails closed.
- The artifact store uses a durably published random marker plus filesystem identity, and every
  resume revalidates exact slot, transfer-pending, finalize-pending, or final physical layout and
  headroom. Revalidation observes and rejects drift; it never repairs untrusted state.
- HTTPS acquisition ignores ambient proxy authority, requires TLS 1.3, reauthorizes every
  redirect against the signed source list, requests exact ranges, rejects compression/chunked
  ambiguity, bounds reads, and verifies every chunk and final artifact digest.
- Offline `bundle://` and online `https://` sources are routed only through an exact closed
  composite adapter. Partial and completed state is journaled, resumable, and published to the
  CAS without replacement.
- ReserveSpace and EnsureComposeBundle are integrated into the parent saga and cross-check the
  reservation, aggregate evidence, complete artifact set, and exact Compose artifact digest.
- Download slots remain separate CAS reservations. A distinct authenticated capacity aggregate
  journals per-artifact Expanded leases plus Rollback and Safety leases against an attested Docker
  backing pool, with a pending state before every physical consume, transfer, or release. Parent
  phases reserve these leases, consume each expanded artifact through an explicit materializer,
  transfer rollback/safety ownership at activation, and release only unconsumed operation-owned
  leases. The Docker adapter now physically reserves exact bytes, binds expanded leases to the
  signed source CAS digest/size, independently journals target consume/transfer/release intent,
  reconciles exact measured engine usage after crashes, and verifies retirement for cancellation,
  transfer, and uninstall. The signed release and install-plan schemas now bind an explicit target
  representation, target-storage identity, authority digest, and exact materialization projection.
  Compose-bundle and Docker image/volume target engines consume only those signed projections and
  retain their independent crash-recovery journals.

### Docker resource and Compose policy

- Signed Compose policy closes profiles, services, image digests, loopback ports, internal
  networks, volumes, labels, health probes, non-root users, read-only roots, capabilities, and
  `no-new-privileges`.
- Docker CLI and Compose are independent, direct executable authorities bound to the same signed
  release-manifest and runtime-plan digests, exact path/digest/owner/publisher, platform,
  architecture, and distinct roles. Ambient `docker compose` plugin discovery is not used.
- The runner holds and revalidates the authorized executable object, requires platform-native
  publisher policy, uses exact argv, a scrubbed environment, explicit local endpoint, bounded
  output, and no command shell. macOS uses Security.framework designated-requirement and
  Gatekeeper assessment, Linux requires an authenticated package receipt, and Windows uses
  WinVerifyTrust plus an exact signer-identity dependency. Unix cancellation supervises the
  complete process group through bounded TERM/KILL. Windows uses
  `PROC_THREAD_ATTRIBUTE_JOB_LIST` to attach the child to its Job Object atomically at creation.
- Managed network and volume reconciliation rejects foreign ownership, duplicate/ambiguous JSON,
  unsafe names, remote contexts, and destructive replacement. Creation is idempotent and
  journaled with a complete inventory digest.
- Compose rendering/config validation/up/wait/probe/down operations are digest-bound and use
  only the signed topology. Compose input and secret materialization is guarded by retained
  descriptor/handle ancestry; the Unix generation directory is host-owner-only while its read-only
  secret leaf remains readable by container UID/GID 10001. There is no Docker socket mount into a
  container.

### Agent configuration

- Host-neutral JSON merge policy preserves unrelated fields, rejects duplicate keys and
  ambiguous ownership, adds one marker-bound AgentMemory entry, and requires the prior managed
  entry digest before replacement.
- The application performs detect/read/validate/plan/compare-and-swap/verify and restores the
  exact backup after a failed invocation when restoration remains conflict-safe.
- Linux, macOS, and Windows filesystem stores implement owner-bound, no-link/reparse, atomic,
  durable, receipt-bound, replay-aware compare-and-swap and conflict-safe restore behavior using
  their platform-specific ACL/DACL and publication primitives. Native certification remains
  outstanding; the production location resolver now selects the documented user-scope Codex
  (`~/.codex/config.toml`), Claude Code (`~/.claude.json`), and Gemini CLI
  (`~/.gemini/settings.json`) files. Generic clients and “GLM” model selection deliberately do not
  manufacture a filesystem format: GLM used through Claude Code/Codex selects that actual host,
  while a genuinely distinct client requires a certified adapter. The signed-launcher MCP
  handshake verifier is not yet implemented.

The host-location projection is based on the vendors' current user-scope contracts:
[OpenAI Codex MCP configuration](https://developers.openai.com/codex/mcp/),
[Anthropic Claude Code MCP scopes](https://code.claude.com/docs/en/mcp), and
[Google Gemini CLI settings](https://codelabs.developers.google.com/gemini-cli-hands-on).
Release certification must revalidate these contracts against every pinned supported host version;
the URLs are design evidence, not a substitute for the signed compatibility manifest.

The native Docker endpoint projection follows Docker's documented local transports: a macOS
unprivileged install can use the owner socket at `~/.docker/run/docker.sock`, Windows uses
`npipe:////./pipe/docker_engine`, and the Engine default on Linux is
`unix:///var/run/docker.sock`. See Docker's
[macOS permission requirements](https://docs.docker.com/desktop/setup/install/mac-permission-requirements/)
and [Docker CLI socket reference](https://docs.docker.com/reference/cli/docker/). The runtime phase
must still attest the live endpoint and must not trust this routing projection as runtime evidence.

- These applications do not substitute for concrete Core/SQLite/Neo4j/provider probes or a Core

## Security, compatibility, and rollback notes

- Bootstrap secrets, provider credentials, source contents, raw process output, and user paths are
  excluded from install evidence. Secret-bearing inputs are represented by protected references.
- The Linux owner-only file fallback does not claim protection from the invoking principal or a
  privileged actor restoring an entire old key/journal/anchor set.
- The macOS Keychain integration test is opt-in because it requires the production signed host,
  entitlement, stable application identity, and unlocked invoking-user Data Protection Keychain.
  A skip is never certification evidence.
- Windows test binaries cross-compile on macOS, but cross-compilation is not native Windows proof.
  The privilege-dependent symlink fixture may skip when the native runner lacks that privilege;
  such a skip is not certification evidence.
- Journal and snapshot DTOs are versioned and reject unknown versions/fields. A future migration
  must be signed, forward-only, and tested, or retain the previous reader for rollback.
- Production composition order is lock -> owner/key binding -> digest locator -> authenticated
  journal -> protected rollback anchor -> operation repository/application -> unlock. Returning an
  undecorated journal or releasing the lock before final persistence violates the design.
- Upgrades may activate only after shadow verification and must retain the prior generation.
  Uninstall never removes a reused runtime and may remove an AgentMemory-provisioned runtime only
  after a second consent and proof that no foreign workload depends on it.

```text
gofmt -l apps/launcher tools

go mod verify
go vet ./apps/launcher/... ./tools/...
staticcheck ./apps/launcher/... ./tools/...
govulncheck ./apps/launcher/... ./tools/...

  -coverprofile=build/go-cover.out ./apps/launcher/... ./tools/...

  -base origin/main -package 80 -changed 90
```

retain the signed-host Keychain/ACL/durability campaign; Linux certification must retain supported
filesystem, rootless runtime, package-signature, privilege, reboot, and power-loss evidence.

## Status rule

Do not change Delivery status to Done or Release status to Releasable until every row in the
acceptance table is Complete, every repository-owned blocker is closed with production code, every
external evidence item is attached to the release, all required artifacts are signed and pinned,
and the complete certified-host test matrix passes without an unapproved skip.
