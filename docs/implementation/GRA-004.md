## Architecture

GRA-004 keeps temporal and VCS policy inside the graph domain. `TruthTemporalScope` accepts only an
unqualified explicit `current` request or an explicitly qualified `historical` request. A historical
request may set valid time, recorded time, or exactly one repository branch/commit selector. All
times are UTC and all result limits are bounded.

`QueryTemporalAssertionsHandler` first resolves a branch to one immutable commit at the requested
recorded-time watermark. It then asks the canonical assertion repository for the assertion revision
valid at `as_of_valid` and known at `as_of_recorded`. The response carries an explicit `current` or
`historical` currency label, lifecycle event, selected assertion revision, temporal coordinates,
resolved commit, graph watermark, force-push signal, and one content-free reachability proof per
evidence item. A historical result can report that the same assertion is currently non-authoritative;
it can never be labelled current.

The application layer depends only on `TemporalAssertionRepository`, `VcsRevisionPort`, and
`VcsRevisionBatchRepository`. SQLite, HTTP, Pydantic, SQLAlchemy, and FastAPI stay in adapters and the
composition root. The repository pattern is authorization-first: current principal, Brain, grant,
Project, Repository, Checkout, and classification scope are verified before candidate or VCS data is
returned.

## Bitemporal semantics

Valid and recorded intervals are half-open:

- `valid_from <= as_of_valid < valid_to`, with null `valid_to` meaning open-ended;
- a lifecycle revision exists only once its immutable lifecycle row was created;
- the preceding active revision receives an exclusive recorded end at the next lifecycle row;
- a disputed revision is historical evidence but is not returned as positive active truth; and
- current queries additionally require the selected revision to remain the current authority.

This supports retroactive knowledge safely. A fact whose valid start predates its activation is absent
from queries recorded before activation and appears in later recorded-time views of that earlier valid
instant.

## Immutable VCS history and branch behavior

`VcsRevisionBatch` records bounded canonical commit nodes, direct parents, ref observations, and
evidence impacts. Batches are digest-bound to Brain, Repository, operation, source, content, and
observation time. Exact retries return the same digest; divergent retries, changed parent sets,
unknown/future parents, cycles, foreign-repository evidence, or unauthorized scopes fail closed.
Incremental batches may reference a commit from an earlier batch, and ref-only observations are
supported.

A branch is never trusted as revision identity. At query time it resolves to the most recent ref
observation known at the requested recorded time. The repository compares that commit with the prior
observation through immutable ancestry; non-descendant movement is marked as a force-push. The graph
watermark binds every included batch digest, making the explanation replay-verifiable.

Non-user evidence is anchored when registered to the latest immutable Checkout commit observed no
later than the evidence occurrence. The migration applies the same rule to existing evidence.
Evidence remains applicable only when its anchor is an ancestor of the selected commit. An impact at
commit `C` stales that evidence only for selected commits descended from `C`. Consequently, a sibling
branch remains valid, a later merge inherits the impact, and a rewritten branch is evaluated against
its new concrete ancestry rather than its reused name.

## Public contract and failures

`POST /graph/revisions/observations` authenticates first, resolves current canonical repository
access, validates canonical ordering and all bounded domain values, and returns an immutable digest
receipt. `GET /graph/assertions/truth` follows the same authorization-first path and accepts only
closed predicates and temporal selectors. No endpoint accepts SQL, Cypher, a dynamic relationship
type, path content, or arbitrary provider data.

Authorization, validation, conflict, integrity, and dependency failures map to stable content-safe
problem responses. Storage details, branch-adjacent source content, SQL, filesystem paths, and raw
exceptions are never returned.
