PRO-006 provides one central, durable scheduler for every provider operation. Callers enqueue only
content-free metadata and a protected local payload reference. The scheduler owns homogeneous
batching, weighted fairness, request and token quotas, concurrency, cost admission, leases,
cancellation, child outcomes, and retry eligibility. Provider-specific HTTP and SDK behavior remains
behind the gateway port and cannot enter the scheduling domain.

## Exact batching contract

`ProviderBatchKey` includes Brain, project, repository, classification, exact profile and version,
embedding space and fingerprint, canonical purpose, provider retention-policy digest,
preprocessing digest, deadline class, and workload. Every field is part of the canonical partition
digest. Project, repository, and workload are included beyond the minimum story requirement so a
batch can never accidentally cross an authorization or priority boundary.

`BatchPlanner` is a pure stable splitter. It rejects mixed partitions, duplicate item IDs, duplicate
operation/ordinal pairs, and an item that cannot fit by itself. It then splits on exact item count,
per-item token, request token, input byte, and batch-cost ceilings without changing caller order,
item identity, or operation ordinal.

Interactive work is structurally tied to the interactive deadline class. Capture, backfill,
evaluation, and maintenance work cannot use that class and are never included in an interactive
batch.

## Fair scheduling and admission

The scheduler uses a closed deterministic weighted cycle:

`interactive, capture, interactive, maintenance, interactive, capture, backfill, interactive,
evaluation`.

Every supported workload has a slot, which bounds starvation to one nine-slot cycle under continuous
load. The cursor is persisted per profile so restart does not reset fairness. Within a selected
profile/workload/partition, due items retain deterministic order by next-attempt time, enqueue time,
ordinal, and item ID.

Admission uses integer-micro request and token buckets to avoid floating-point drift. The same pure
rate state enforces provider retry hints, maximum concurrency, and the configured monthly cost
budget. Claiming a batch, advancing the fair cursor, consuming rate/cost authority, creating the
lease, and appending the batch/item evidence happen inside one `BEGIN IMMEDIATE` transaction.

## Authorization and payload containment

Enqueue validates current identity scope and stores only metadata, hashes, counts, policy
coordinates, and a protected `cas://`, `artifact://`, or `local-object://` reference. Read and cancel
are Brain-scoped and do not reveal cross-Brain existence.

After a lease is acquired, `ProviderSchedulerWorker` reauthorizes each immutable child immediately
before materialization. The SQLite authorization adapter rechecks the Brain, principal, current
grant version, authorization policy version, security epoch, exact active profile revision,
embedding space and fingerprint, scope coordinates, content digest, payload reference,
cancellation flag, and deadline. A denial prevents gateway invocation. Materialized payloads are
mutable buffers and are overwritten in `finally` on success, denial, malformed response, dependency
failure, or task cancellation.

The worker depends on three narrow ports:

- `ProviderDispatchAuthorizationPort` performs the mandatory final egress decision;
- `ProviderPayloadMaterializer` resolves only the authorized protected local reference; and
- `ProviderBatchGateway` executes one homogeneous, language-neutral provider operation.

PRO-006 does not bypass the provider execution boundary. Each built-in or custom execution adapter
must bind those ports when its operation is enabled. This preserves Clean Architecture and ensures
future retry, containment, and endpoint-equivalence stories can wrap one stable dispatch contract.

## Durable lifecycle and partial results

Work moves through queued, leased, retry-scheduled, completed, cancelled, or failed states. Leases
are owner-bound and recoverable after expiry. Cancelling queued or retry-scheduled work is immediate;
cancelling leased work persists `cancel_requested`, causing the final authorization check to deny
dispatch.

Every batch has a generated operation ID and immutable ordered child membership. A provider response
must have the same batch operation ID and exactly one ordered result for each child. Successful,
retryable, permanent, and cancelled results are journaled individually. Only retryable children
return to the queue, with the maximum applicable child/provider retry hint; other children close
atomically. Malformed, duplicate, missing, reordered, or foreign child results fail closed.

Enqueue and cancellation have immutable idempotency receipts. Reusing an operation identity with
different request coordinates conflicts. Work identity, batch membership, and child results are
protected by SQLite foreign keys, constraints, and immutable-history triggers. Downgrade is allowed
only while every PRO-006 authority table is empty.

## Clean Architecture

- `providers.domain.scheduling` owns immutable queue values, pure batching, fair selection, rate
  admission, leases, and result validation.
- `providers.domain.scheduling_ports` owns repository, identity, final authorization, payload, and
  gateway abstractions.
- `providers.application.scheduling` owns exact action authorization, enqueue/read/cancel handlers,
  and worker orchestration.
- `SqliteProviderSchedulingRepository` is the single canonical queue and evidence repository.
- `SqliteProviderDispatchAuthorization` is the final transactional authority recheck.
- `scheduling_http_api` authenticates before scope resolution, requires exact idempotency keys,
  rejects unknown fields, and emits content-free problem responses.
- `operations.bootstrap` is the sole production HTTP composition root.

The domain and application layers import no SQLAlchemy, FastAPI, Neo4j driver, vendor SDK, or
provider-specific protocol.
