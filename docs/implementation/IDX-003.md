## Architecture and invariants

IDX-003 extends the indexing bounded context through Clean Architecture ports. The domain owns
revision contexts, graph answers, applicability policy, and re-extraction identities. Application
handlers orchestrate processing, history queries, and evidence-lineage registration. SQLite, Git,
FastAPI, and the existing graph truth implementation remain adapters. No domain or application
module imports a persistence, transport, Git, or framework concern.

Every changed or deleted file in a completed committed index run becomes one immutable
`SourceRevisionTransition`. Its digest binds the run and event, Brain/Project/Repository, current
and previous source identities, snapshots, file revisions, paths, commit coordinates, content
digests, semantic units, evidence, assertions, reintroduction link, and occurrence time. The
derived context identity also includes event, snapshot, revision, file, and commit. Reintroducing
identical bytes after a revert or deletion therefore creates a new context and re-extraction job;
content identity can never imply uninterrupted validity.

`IndexRevisionContext` separates immutable committed indexing from mutable worktree indexing.
The Git adapter marks an explicit target commit or a clean checkout as `committed`, and a staged,
unstaged, or untracked checkout as `worktree`. Legacy runs without the new row are conservatively
decoded as worktree runs. Existing worktree projection delivery keeps its immediate global-current
evidence revocation behavior. Committed events do not globally dispute an assertion: IDX-003 adds
an ancestry-scoped `vcs_evidence_impacts` record, so GRA-004 truth queries stale it only on branches
that contain the invalidating commit.

## Pinned commit-graph authority

`CommitGraphPort` reads the canonical VCS DAG already persisted by GRA-004; the persistent Core
never mounts or shells into a repository. A history query resolves its branch or commit once and
creates a `CommitGraphSnapshot` containing the selected target, explicit recorded time, ref
observation proof when applicable, and a digest of every visible commit, parent edge, and ref
observation. Every ancestry answer used by that query is evaluated against this same digest.
Concurrent ref movement cannot mix graph states within one result.

Ancestry uses parent-link reachability. Merge-base returns every best common ancestor rather than
an arbitrary first result. The adapter persists each answer under a natural query key containing
Brain, Repository, question, commits, and graph digest. Repeating the same pinned question returns
the original answer ID and original answer time. This follows Git's documented reachability model
and its warning that more than one best merge base can exist:

- [git-rev-list parent and ancestry traversal](https://git-scm.com/docs/git-rev-list)
- [git-merge-base `--all` and `--is-ancestor`](https://git-scm.com/docs/git-merge-base)

Force-push is handled without mutating history. A later ref observation can select a rewritten
tip, but earlier snapshots and answers remain replayable at their recorded time. Cherry-picks are
distinct commit contexts even when patch content is equivalent. Merge reachability naturally
propagates invalidations only when the invalidating commit is an ancestor of the selected merge.

## Reverse lineage and temporal validity

`SqliteSourceRevisionRepository` leases only unprocessed projection events whose run is explicitly
committed and has a commit ID. It revalidates the recorded principal, role, scope fingerprint, and
current Repository grant before claiming and again before completing. Completion atomically:

1. appends the new source-revision context;
2. records the prior context's invalidating commit at the source event time;
3. carries exact source → evidence → assertion reverse lineage;
4. appends missing branch-aware evidence impacts to the canonical VCS ledger;
5. creates an `extract` or `retract` re-extraction job; and
6. appends a processing receipt with graph watermark and answer IDs.

Event time governs the revision effect; processing time remains on the audit receipt. This avoids
worker scheduling changing historical truth. A query's `recorded_at` bounds contexts,
invalidations, lineage, commit/ref observations, and assertions. A reachable non-deletion context
with no reachable invalidation is `current`; a reachable invalidation makes it `stale`; a reachable
deletion context is an explicit `deleted` marker. Contexts whose introducing commit is not an
ancestor of the selected revision are omitted.

Lineage registration is an authorized idempotent command. An operation ID exactly replays only the
same context/evidence/assertion tuple; reusing it for different input is a conflict. Evidence and
assertion must already belong to the same Brain, Project, and Repository authority as the source
context. The repository never stores source bytes in the history API or logs.

## Durable schema and rollback

Migration `0028_idx003_revision_history` adds append-only ledgers for run revision context, commit
graph answers, source contexts, invalidations, evidence lineage, registration receipts,
re-extraction jobs, claims, and processing receipts. SQLite constraints enforce closed enums,
commit and digest shapes, result shapes, cardinality, and foreign-key lineage. Update and delete
triggers protect every new table.

An empty migration can round-trip to IDX-002. Once any IDX-003 row exists—including a run context,
claim, graph answer, lineage edge, job, or receipt—downgrade refuses to erase it. Operators must use
the signed backup/restore and release rollback workflow rather than editing Alembic state or
dropping immutable history.

## HTTP and local runtime composition

The local Core exposes:

- `GET /v1/indexing/source-revisions/history` with one exact branch or commit selector; and
- `POST /v1/indexing/source-revisions/lineage` with a matching `Idempotency-Key`.

Both routes authenticate before resolving current Repository authority. Strict request models
reject unknown fields, the history query is bounded to 1,000 rows, and responses contain only
identities, hashes, classifications, timestamps, and graph proof IDs. Error responses are fixed and
do not echo paths, source, branch names, IDs, or credentials. The deterministic public OpenAPI uses
application use-case names as operation IDs.

The production composition root runs `SourceRevisionWorker` under the same graceful-stop lifecycle
as other local Core workers and wires the real SQLite repositories into the authenticated router.
All storage, graph decisions, jobs, and APIs remain on the user's machine.
