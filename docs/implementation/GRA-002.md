## Outcome

GRA-002 prevents an extractor, model, agent, or caller from turning an unsupported subject–predicate–
object claim into authoritative graph truth. A proposal is an immutable `AssertionCandidate`. It can
become active only after exact evidence resolution, current authorization, temporal checks, and the
closed evidence policy all succeed. Active assertions retain their complete scope, valid and recorded
times, three confidence components, extractor/model revision, evidence snapshots, content fingerprint,
and assertion revision.

The feature is agent-neutral. Codex, Claude, Gemini, GLM, generic MCP clients, and future extraction
workers use the same application commands and repositories. Host identity and model output are
provenance; neither is authority.

## Clean Architecture and SOLID boundaries

- `graph.domain.assertions` owns the aggregate, value objects, closed registries,
  `EvidencePolicy`, `TemporalPolicy`, lifecycle events, fingerprints, and transitions. It imports no
  SQL, HTTP, Neo4j, provider, or host SDK.
- `graph.domain.assertion_ports` separates assertion persistence, evidence resolution, and trusted
  evidence-catalog capabilities. Application handlers do not depend on SQLite.
- `graph.application.assertions` owns `ProposeAssertionCommand`, `ActivateAssertionCommand`,
  `ReconcileAssertionEvidenceCommand`, their handlers, and the stateless `AuthorizationPolicy`.
- `graph.adapters.outbound.sqlite_assertions` implements the repository pattern with a fresh
  `AuthorizedScope`-bound capability per operation. It maps immutable aggregates to append-only SQL
  ledgers and verifies every row while reading it back.
- The graph import-linter contracts enforce inward dependencies. Domain and application code remain
  framework-independent and adapters cannot become ambient global repositories.

These narrow interfaces preserve single responsibility and interface segregation. Stateless policy
objects and repository ports preserve dependency inversion and make every transition unit-testable.

## Authority and evidence policy

`AssertionPredicate` is a closed enum. Subject, object, assertion, evidence, event, Brain, project,
repository, and optional Checkout identities are UUIDv7 values. Caller text, URLs, Cypher fragments,
and arbitrary relationship names cannot enter the evidence or predicate registries.

An evidence handle can reference exactly one of:

1. a captured canonical event;
2. a captured `prompt.received` event made by the currently authorized owner, which is explicit user
   authority;
3. a CAS artifact bound to the captured event whose `payload_ref` names it; or
4. a half-open byte span inside that same artifact.

The repository derives event digests from `agent_event_envelopes.canonical_sha256`, artifact digests
from `artifacts.sha256`, and span digests from the artifact digest plus exact start/end offsets. The
caller supplies none of those digests. Registration rejects a mismatched event kind, wrong artifact,
out-of-range span, future source, wrong owner, inactive grant, wrong Brain/scope, or classification
above the scope ceiling.

Explicit user-statement evidence may activate one claim without an automated confidence threshold.
Automated activation requires all three confidence components to be at least 7,000 basis points and
at least two independent canonical source IDs. In both cases the evidence-ID set must exactly equal
the candidate set; every source must be immutable, currently accessible, not deleted/revoked, in the
exact assertion scope, and already observed by activation time.

## Temporal, authorization, and identity rules

Candidate recorded intervals are open-ended. Activation cannot predate proposal recording or any
supporting evidence. Active assertions start a new recorded-time interval at activation while retaining
the candidate's valid-time interval. Dispute closes the recorded interval with an exclusive end.

The application `AuthorizationPolicy` verifies the action, Brain, project, repository, Checkout, and
classification ceiling. SQLite repeats current principal/Brain/grant checks inside the write
transaction. Reads prefilter in SQL and decode defensively. Cross-Brain or revoked-scope rows are not
returned, even if a caller guesses a stable ID.

Candidate content fingerprints bind all claim coordinates, confidence, extractor identity, evidence
IDs, and temporal values. Revision IDs bind the stable assertion ID to that fingerprint. Lifecycle
event digests bind event/operation/assertion/revision/status/evidence/time metadata and carry no source
content, prompt, artifact bytes, hidden reasoning, or credentials.

## Atomic persistence and idempotency

Migration `0021_gra002_evidence_assertions` creates six constrained tables:

- `assertion_evidence_sources` — immutable verified source handles;
- `assertion_evidence_revocations` — immutable withdrawal facts;
- `assertion_operations` — exact request/result receipts;
- `assertion_candidates` — immutable unsupported proposals;
- `assertion_lifecycle` — append-only active/disputed aggregate revisions; and
- `assertion_evidence_snapshots` — activation-time evidence metadata.

Proposal, activation, and dispute use `BEGIN IMMEDIATE` under the process writer lock. Activation
inserts its operation receipt, `AssertionActivated` domain event, lifecycle row, and evidence snapshots
in one commit. Exact operation retries compare scope, principal, request digest, event ID, status, and
version and return the original aggregate. Divergent reuse fails with `GraphConflictError`; no row is
overwritten.

Evidence revocation and its consequences are also one transaction. After appending a revocation, the
repository resolves every active dependent assertion's complete evidence set. Assertions retaining at
least one usable source remain active. Every newly unsupported assertion transitions through the
domain aggregate and atomically appends an `AssertionDisputed` event and lifecycle revision before the
revocation commits. A crash therefore cannot commit revoked support while leaving its unsupported fact
active.

SQLite checks enforce closed statuses, predicates, classifications, confidence ranges, source shapes,
JSON validity, intervals, digests, foreign keys, and aggregate-version transition shapes. Update/delete
triggers protect all six ledgers and assertion domain events. Downgrade is permitted only before any
GRA-002 evidence, operation, or revocation exists; otherwise it refuses.

## Deletion, tombstones, and repair

Resolution treats an evidence revocation or matching `assertion_evidence`, `agent_event`, or `artifact`
deletion tombstone as unavailable. Tombstone-driven or authorization-driven changes are handled by
`ReconcileAssertionEvidenceCommand`, which repeats the complete policy and atomically disputes an
unsupported active assertion. Historical activation snapshots remain immutable for explanation and
audit; they never restore current authority.

Never repair an assertion, evidence handle, operation receipt, lifecycle row, snapshot, or assertion
domain event in place. Quarantine the affected identity, preserve content-free diagnostics, repair the
canonical captured event/artifact or grant through its owning workflow, and replay the governed
command. Follow [the GRA-002 runbook](../runbooks/GRA-002-ASSERTION-EVIDENCE.md).
