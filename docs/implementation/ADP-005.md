ADP-005 completes the interrupted-capture path introduced by ADP-002. Every supported host adapter
uses the same canonical `AgentEvent` bytes and can defer them into the bounded encrypted local spool.
The installed launcher supervises `agentmemory-spool-worker`; the user does not run a repair command,
understand Docker, or configure a database. When the local Core is stopped, restarting, or being
upgraded, the worker retains the ciphertext and retries. After Core recovers, it drains bounded batches
and erases only events for which Core returned item-specific durable evidence.

## Clean Architecture and SOLID boundaries

- `ingestion.domain.spool_reconciliation` owns immutable spool coordinates, the closed upload-result
  vocabulary, signed clock-skew evidence, and deterministic contiguous-prefix acknowledgement policy.
- `OfflineSpoolRepository`, `SpoolBatchUploader`, and `RecoveryScheduler` are narrow capability-specific
  ports. They do not expose SQLite, HTTP, process, or cryptography types to application code.
- `ReconcileSpoolHandler` owns one bounded lease-protected use case. `SpoolRecoveryWorker` owns retry,
  fairness, and shutdown policy without knowing how the spool or Core is implemented.
- `EncryptedSqliteSpool` and `SqliteOfflineSpoolRepository` own all local queue SQL, encryption,
  watermarks, lease persistence, filesystem permissions, and secure deletion.
- `HttpSpoolBatchUploader` owns the fixed loopback transport and strict response decoding.
  `spool_recovery_cli` is the composition root and the only layer that reads protected config/secrets,
  constructs HTTP clients, installs shutdown signals, or selects concrete adapters.

These boundaries preserve dependency inversion and single responsibility. Recovery policy can be
tested with in-memory ports, SQLite can be tested without FastAPI, and the Core batch boundary can be
tested without the worker. No host name, model provider, or Docker implementation appears in the
domain/application layers.

## Queue, encryption, and filesystem safety

The spool stores the exact already-validated, already-redacted canonical event bytes. Each item uses a
fresh 96-bit nonce and AES-256-GCM under a dedicated protected 32-byte spool key. Authenticated
associated data binds event ID, ordering key, and original event sequence. A SHA-256 digest of both the
canonical plaintext and AAD detects conflicting identity reuse and storage corruption before delivery.
Keys and canonical bytes are never written to logs, responses, watermarks, or recovery configuration.

The database parent must be an existing owner-private directory. A new database is created with mode
`0600` before SQLite opens it; existing symlinks, non-regular files, foreign ownership, or group/other
permissions fail closed. SQLite uses WAL, `synchronous=FULL`, foreign keys, `secure_delete=ON`, and a
bounded busy timeout. Defaults cap pending data at 10,000 events and 64 MiB. One event is limited to
96 KiB, one upload to 100 events and 1 MiB of canonical bytes, and all configuration values have finite
upper bounds. Capacity exhaustion returns `spool_full`; it never evicts an older unacknowledged event.

## Ordering, concurrency, and watermarks

Delivery order is deterministic per ordering key: explicit event sequence first, then insertion order
for events without a sequence. A window function assigns a repository-owned `spool_sequence` after the
last acknowledged watermark. Upload response order is required to match request identity order exactly.

One persisted singleton lease serializes recovery processes and is recoverable after its wall-clock
expiry. A live foreign owner receives `busy` and performs no upload. The repository rechecks the exact
owner and expiry inside the same `BEGIN IMMEDIATE` transaction that advances watermarks and deletes
ciphertext. A forward clock jump can expire the old lease but also prevents its old owner from ACKing;
a backward jump retains the existing lease conservatively. Shutdown always releases an owned lease,
while crash recovery relies on the finite expiry.

For each ordering key, only the contiguous durable prefix can advance. If item `a-1` is retryable and
`a-2` is accepted, neither is erased; an accepted item under an independent key can still advance. The
repository independently reconstructs the current prefix before deletion, so a stale, non-prefix,
wrong-owner, or expired acknowledgement fails without mutation. Accepted and duplicate evidence is
stored only as content-free event/time/disposition metadata. After commit, a WAL truncate checkpoint
removes obsolete ciphertext pages.

## Core batch contract and time semantics

The batch endpoint authenticates the installation capability once and validates the entire outer JSON
document and every event before the first side effect. It rejects duplicate JSON keys, unknown fields,
empty/oversized batches, invalid UTF-8, and more than 100 items. Valid items are appended independently
through the existing ADP-002 handler and transaction, yielding exactly one ordered result:

- `accepted` or `duplicate`, with server ingestion microseconds and signed clock skew;
- `retryable`, when a dependency did not establish durability;
- `rejected`, for validation or authorization failure; or
- `conflict`, for immutable ID/content/order reuse.

Only the first two are deletion authority. A whole-request non-success becomes non-durable per-item
results, and a network failure leaves the batch untouched. Redirects are never followed. The uploader
accepts only HTTP loopback (`127.0.0.1` or `::1`), a 32-byte capability, a bounded response, exact JSON
keys/types, exact item count, and exact ordered event IDs.

The canonical event's `time`/`occurred_at` is never rewritten. Core separately records and returns the
actual ingestion time and `ingested_at - occurred_at` in signed microseconds. Exact duplicate retries
return the original stored ingestion time and clock skew, not the retry time. This distinction survives
replay and is persisted in the spool watermark before local erasure.

## Automatic recovery lifecycle

The launcher writes an owner-only bounded configuration and starts `agentmemory-spool-worker` with the
host adapter. The worker initializes or upgrades the local spool schema, reads the protected API and
spool keys, and polls indefinitely. It rapidly drains successful batches up to a fairness cap, backs off
for blocked/unavailable batches, sleeps while idle, and responds to SIGINT/SIGTERM without writing to
stdout. Core/container restarts require no user action. A stable content-free error is written to stderr
only when protected configuration or startup composition fails.
