# PRO-009 implementation record

| Field | Value |
|---|---|
| Story | PRO-009 — Contain provider data and runtimes |
| Delivery status | Release-qualified containment boundary; dependent provider execution composition remains fail-closed |
| Default posture | Offline; no egress network and no provider gateway |
| Remote posture | Optional signed topology with one dual-homed gateway |
| Canonical authority | SQLite provider profiles, active egress policy, immutable permits, and content-free decision evidence |
| Runtime authority | Immutable launcher `PolicyPlan` and per-operation custom-adapter `DeploymentPlan` |
| Relational migration | `0042_pro009_provider_containment` |
| Public administration API | `POST /v1/provider-containment/policies`, `GET /v1/provider-containment/policies/active` |
| Internal gateway API | Authenticated `POST /v1/provider-operations/execute` and `POST /v1/health` |

PRO-009 adds two independent containment layers. Core decides whether one exact operation may
leave the machine and signs a short-lived, content-free permit. The isolated gateway independently
authenticates the caller, verifies the permit, reserves replay/rate/token/budget capacity, resolves
only the credential bound to the active profile attestation, validates DNS and the direct TLS
connection, performs one bounded request, destroys mutable secret buffers, and records only a closed
decision fact. Custom adapters execute in a separate operation-scoped container and never receive a
provider credential, project, database, host path, or Docker socket.

## Clean Architecture boundaries

- `providers.domain.containment` owns the immutable taint, destination, route, policy, request,
  permit, sandbox, gateway credential, HTTP response, result, and telemetry contracts. It imports no
  SQL, HTTP, Docker, FastAPI, or provider SDK.
- `providers.domain.containment_ports` defines final authorization, context resolution, permit
  encoding, credential brokering, pinned transport, adapter supervision, and evidence ports.
- `providers.application.containment` owns policy commands/queries, final authorization ordering,
  payload destruction, sandbox execution, and safe runtime telemetry.
- `providers.application.gateway` builds the final authorization request and independently executes
  a signed gateway command.
- SQLite, protected-file, encrypted-vault, internal HTTP, DNS/TLS, append-only telemetry, FastAPI,
  Compose, Docker CLI, and secret projection are outbound or inbound adapters.
- The Go launcher owns container-engine authority. Core and the gateway have no Docker socket.

The repository layer uses `SqliteProviderContainmentRepository`; application handlers never issue
SQL. The topology and sandbox constructors are closed value objects rather than user-authored
Compose documents. This keeps the dependency direction inward and prevents framework or vendor
details from becoming domain authority.

## Final egress authorization

`ResolvedProviderEgressRequestFactory` prepares the vendor wire body before authorization and hashes
it without retaining another plaintext copy. `SqliteProviderEgressOperationContextResolver` then
requires all of the following to still match:

- Brain and optional project;
- active profile ID and exact optimistic version;
- active capability-attestation ID, adapter digest, configuration digest, endpoint fingerprint,
  model revision, operation type, and purpose;
- exact policy route, HTTPS hostname/port/path prefix, declared region, retention, training,
  quota, budget, timeout, and current installation security epoch; and
- immutable content classification plus irreversible private-block and secret-bearing taints.

`ProviderEgressPolicy.authorize` permanently denies `restricted`, `local_only`, private-block, and
secret-bearing input. It also denies any classification above the policy ceiling, stale policy,
disallowed region, non-exact route, excessive retention/training, size, timeout, quota, token, or
budget coordinate. There is no override field or alternate allow path.

Authorization persists an immutable permit before `ContainedProviderEndpointGateway` can invoke the
socket port. The HMAC token binds every request coordinate, including wire-body digest, content
digests, destination, profile attestation, model revision, policy/security versions, limits,
accounting, issue time, and expiry. The gateway rechecks body digest and token lifetime and rejects
replay independently.

Remote profile activation uses the same boundary rather than an unsigned bootstrap exception.
`ContainedProviderProfileProbeTransport` submits the exact draft profile/version/configuration
digest to `SqliteProviderContainmentRepository.authorize_probe`. A provisional immutable policy
route must bind those coordinates, the configured model, destination, operation, purpose, path, and
credential reference. Core then signs a short-lived provisional permit and sends only that permit,
path, and fixed public-canary body to the gateway. Policy and secret references never cross the
process boundary. After successful activation, credential and policy bindings are republished under
the resulting immutable capability-attestation ID before billable work is eligible.

## Gateway network boundary

The optional remote `PolicyPlan` adds `am_egress`; `am_internal` remains an internal bridge. Only
`provider-gateway` joins both networks. Core, Neo4j, local providers, migration, secret projection,
and custom adapters remain on `am_internal` or have networking disabled. The gateway has:

- a digest-pinned dedicated image, non-root `10001:10001`, read-only root filesystem, all
  capabilities dropped, `no-new-privileges`, bounded tmpfs/CPU/memory/PIDs, no host port, no build,
  no Docker socket, and no state/artifact/database mount;
- one read-only least-privilege secret volume and the append-only telemetry volume;
- a fixed internal hostname, port, Host header, route set, capability authentication, strict JSON,
  bounded body, and no proxy/environment inheritance; and
- direct HTTPS only. The transport validates the complete DNS answer, denies private, loopback,
  link-local, multicast, unspecified, reserved, IPv4-mapped-private, and metadata addresses, pins the
  selected numeric address while retaining the approved hostname for Host/SNI/certificate
  verification, requires TLS 1.2 or newer, disables redirects and proxies, and enforces request,
  response, header, path, and deadline limits.

A redirect is denied and must return to Core for a newly authorized operation. The gateway never
acts as a CONNECT proxy and exposes no generic URL, method, header, or credential-resolution API.
The cancellation-safe transport uses an asyncio-owned TLS stream rather than a detached blocking
thread, so cancellation closes and awaits the socket before returning. Its bounded HTTP/1 parser
rejects ambiguous framing, folded headers, excessive headers, unsupported transfer codings, and
incomplete bodies. The gateway discards all provider response headers except one syntactically
valid, non-ambiguous `Retry-After`; it normalizes that value to an absolute epoch-microsecond time
bounded to seven days before the authenticated internal response crosses back to Core.

## Credential projection and memory handling

Remote topology accepts exactly five owner-protected source files:

1. internal client capability;
2. permit HMAC key;
3. authenticated encrypted credential vault;
4. vault AES-256-GCM key; and
5. independent vault HMAC-SHA256 key.

The one-shot, network-disabled root secret projector creates three engine-managed volumes:

- `provider-core-egress`: client capability and permit-signing key, owned by `10001:10001`;
- `provider-gateway-secrets`: client capability, permit key, encrypted vault, encryption key, and
  vault authentication key, owned by `10001:10001`; and
- `provider-adapter-egress`: client capability only, owned by `65532:65532`.

Every projected file is a regular, single-link, owner-only `0400` file copied through descriptor-
bound no-follow operations. Cryptographic values are exactly 32 bytes; the encrypted vault is
bounded to 4 MiB. The projector rejects unexpected volume contents, unexpected capabilities,
network routes, secret material in process arguments/environment, ownership/mode drift, input races,
or non-durable replacement.

`EncryptedProviderCredentialVault` authenticates the complete canonical vault and decrypts every
entry during gateway composition, then re-reads and reauthenticates the snapshot for every operation.
Entries are sorted and unique by `(profile_id, profile_attestation_id)` and bind the approved header,
prefix, nonce, and ciphertext through AES-GCM additional authenticated data. Plaintext is returned
only in a caller-owned `bytearray` and is overwritten after the socket call. The vault document,
exceptions, representation, API responses, and telemetry contain no credential value.

Credential entry, rotation, and OS credential-facility integration remain the product credential
management surface defined by PRD Sections 7.2 and 9.3. PRO-009 consumes only its protected encrypted
source artifacts and deliberately does not create a second plaintext credential API.

## Activation boundary versus execution composition

The governed remote profile probe and isolated custom-adapter runtime are enabled production paths.
The PRO-006 billable scheduler and PRO-008 provider-backed migration endpoint remain deliberately
fail-closed in Core until their protected payload/result-CAS adapters and operation-specific wire
codecs are composed through `ContainedProviderEndpointGateway` and
`ResilientProviderOperationHandler`. No direct vendor adapter or placeholder socket path is enabled.
Those integrations are tracked as remaining full-product work and must be completed before the
corresponding provider-execution and migration stories can be considered end-to-end release-ready;
they are not claimed as PRO-009 containment evidence.

## Custom-adapter sandbox

`ProviderAdapterOperationSupervisor` derives one project and service name from the immutable adapter
plan digest plus operation ID. It validates the strict framed request before creating a container.
The closed Compose document has one digest-pinned image, one internal network, a read-only root,
non-root `65532:65532`, `init`, all capabilities dropped, `no-new-privileges`, no restart, no ports,
no environment, no build, no bind mount, and a `noexec,nosuid,nodev` operation tmpfs with hard
CPU/memory/PID/time limits.

Gateway capability is mounted only for an operation whose signed manifest requested mediated gateway
access. Persistent installation/conformance containers receive no gateway capability. Operation
content travels only through bounded framed stdin; bounded framed stdout must match the request ID,
operation ID, content IDs, and protocol result contract. Stderr is discarded at this boundary.

Compose runs with `--rm --no-deps -T`, then `down --remove-orphans` executes under an independent
cleanup timeout for success, failure, timeout, cancellation, malformed output, and panic-safe return
paths. Startup reconciliation lists containers only by the exact managed/kind/plan labels, rechecks
the full immutable container ID and operation labels, removes only proven-owned orphans, and proves
the authorized set empty before accepting work.

## Telemetry and persistence

The migration adds versioned immutable egress policies, one active-policy pointer, idempotent policy
operations, short-lived permits, adapter runtime facts, and gateway decision facts. Triggers reject
mutation/deletion of historical facts and unsafe pointer changes. A downgrade refuses to destroy
existing authority or evidence.

Allowed telemetry fields are fixed:

- gateway: permit digest, operation ID, destination fingerprint, closed outcome code, request and
  response byte counts, status code, and time;
- custom runtime: operation ID, adapter image digest, closed outcome code, runtime milliseconds,
  cleanup digest, and time.

Content, prompts, paths, repository names, payloads, response bodies, vectors, credentials, secret
references, DNS addresses, and arbitrary exception text have no field in these records.
