## Domain model and conflict rules

Contradiction is explicit domain state, never a rank penalty. Every canonical assertion now carries
closed `positive` or `negative` polarity. Existing positive assertion fingerprints remain stable;
negative polarity is included in new fingerprints and persisted with the candidate. Detection reads
only current active assertions with immutable evidence snapshots.

The versioned rule table recognizes opposite polarity for the same subject, predicate, object, and
overlapping half-open valid time. It also recognizes different positive objects for the closed
single-valued `deployed_as` predicate. Other predicates remain multi-valued, so differing objects do
not create false disputes. Non-overlapping intervals never conflict. Model-only candidates are not
decisive and cannot establish a dispute.

Each conflict has a stable digest identity over its assertion pair, dimension, overlap, evidence,
and policy version. The detection observation has a separate time-bound digest. Exact operation
replay succeeds; reuse with a different observation fails. Repeated scans do not create a second
conflict fact.

## Resolution and retrieval behavior

A resolution is append-only and binds the contradiction, outcome, current actor, current grant,
reason code, authorized evidence IDs, resolution time, and policy version. The original dispute row
and evidence links remain immutable. Outcomes select the left assertion, select the right assertion,
confirm both as contextually valid, or reject both.

`ContradictionPolicy` runs after candidate fusion and before response synthesis. When both sides of
an unresolved decisive conflict are present, the decision is `unknown` and selection is empty,
regardless of rank. One visible side is `qualified` because the authorized result remains limited by
an unresolved dispute. A resolution filters candidates according to its explicit outcome. Rank is
used only to order the remaining selected assertions.

## Security and architecture

The application layer depends only on `ContradictionRepository`. SQLite, SQLAlchemy, FastAPI,
Pydantic, identity scope resolution, and HTTP problem mapping remain in adapters and the composition
root. Every repository operation validates the requested action and current Brain, principal, grant,
Project, and Repository authority before returning candidates, counts, disputes, or resolution
state. Resolution evidence must be current, unrevoked, and in the same authorized Repository.

The HTTP adapter authenticates before scope resolution or repository access, accepts only closed
DTOs, and returns content-free errors. It never accepts source content, SQL, Cypher, relationship
types, or arbitrary ranking policy.
