MEM-004 implements correction as a new immutable assertion, never as an update to the source
statement. The source identity, content, evidence, provenance, and historical time range remain
queryable. Only lifecycle metadata changes through an optimistic compare-and-swap transaction.

## Architecture

The implementation follows the existing Clean Architecture boundary:

- `memory.domain.correction` owns correction assertions, `SUPERSEDES`/`CONTRADICTS` relations,
  bitemporal history, scope narrowing, optimistic versions, canonical receipts, and deterministic
  precedence. It imports no SQL, HTTP, graph driver, or framework type.
- `memory.application.correct_memory` owns authorization-first command orchestration. It resolves
  the exact target and optional evidence outside the writer, repeats authorization and equality
  checks inside a serialized Unit of Work, and commits only the request-bound result.
- `memory.application.query_memory_corrections` reconstructs complete history and applies the pinned
  precedence policy at an explicit query scope, valid time, and recorded time.
- `SqliteMemoryCorrectionRepository` implements repository ports, owner authorization joins,
  canonical reconstruction, correction history, evidence validation, compare-and-swap transition,
  graph event, outbox, receipt, and audit chain in one SQLite transaction.
- `correction_http_api` performs strict transport validation and authentication before invoking the
  application layer. Missing and unauthorized targets have the same `AM_NOT_FOUND` response.

The composition root constructs dependencies explicitly. Domain and application code depend on
protocols, not adapters, preserving Dependency Inversion and allowing another local database adapter
to pass the same contract suite.

## Correction and precedence rules

Every command binds operation, actor, grant, Brain, correlation, causation, target assertion,
expected aggregate version, statement, scope, valid range, reason, optional evidence, request time,
and deadline into a canonical request digest. Exact retries return the stored receipt. Reusing an
operation with different coordinates fails with a conflict.

A correction may use the source scope exactly or add a checkout to a project/repository-scoped
source. It may never change Brain, project, repository, remove an existing checkout, or rebind to a
sibling checkout:

- an equal-scope correction closes the source recorded-time range;
- a checkout-narrower correction leaves the source recorded range open so it remains applicable in
  other checkouts;
- at query time, the most specific applicable assertion wins, followed by latest recorded time and
  assertion ID for deterministic tie-breaking;
- superseded and disputed assertions remain eligible for historical recorded-time queries during
  their half-open recorded ranges;
- a later correction may target the active correction, creating a fully linked chain.

The relation is `CONTRADICTS` when normalized semantic subjects match and polarity flips; otherwise
it is `SUPERSEDES`. The source becomes `disputed` or `superseded` respectively. A stale version or
closed source fails without a partial write. A narrower source whose recorded range remains open can
receive another explicitly scoped branch; serialized CAS prevents silent concurrent replacement.

## Authorization, evidence, and privacy

Correction is an explicit-user operation. The SQLite authorization join requires an active owner
principal, active Brain, unexpired exact grant, scope coverage, and a write-capable owner/admin/editor
role. Worker, reader, auditor, revoked, expired, wrong-Brain, wrong-project, wrong-repository, and
wrong-grant requests do not reveal whether the target or evidence exists.

Optional evidence must resolve as an exact sorted UUIDv7 set in canonical `event_task_lineage`, must
exist in `agent_events`, must belong to the same Brain, and must be covered by the same current grant.
Each link stores the canonical event SHA-256. Missing or unauthorized evidence rejects the entire
command. An empty evidence set is valid because the explicit user correction is authoritative.

Public conflict and error responses contain no source statement, candidate content, path, prompt,
provider exception, or authorization detail. The correction receipt is content-free. Full history
is returned only after exact authorization.

## Atomic persistence and graph replay

One `BEGIN IMMEDIATE` transaction performs all of the following:

1. authenticates the stored idempotency receipt or inserts a new request-bound receipt;
2. reauthorizes and compares the complete target snapshot;
3. updates only source lifecycle, recorded end, aggregate version, and update time through CAS;
4. inserts the new immutable correction assertion and optional canonical evidence links;
5. appends a `MemoryCorrected` graph projection source containing a new assertion node and a closed
   `SUPERSEDES` or `CONTRADICTS` relationship to the exact source assertion;
6. appends `memory.corrected.v1` to the durable outbox; and
7. appends `memory.corrected` to the tamper-evident audit hash chain.

Any integrity, uniqueness, authorization, version, event, outbox, or audit failure rolls back every
step. The graph event is canonical; PF-002 can rebuild graph state without reading mutable correction
tables or reviving deleted data.
