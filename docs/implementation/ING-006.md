## Outcome

Event capture now records schema family, compatibility major, revision, and original canonical digest
in the same transaction as the immutable encrypted event. Migration `0014` backfills this lineage for
all older encrypted events without decrypting or rewriting them. The original envelope remains the
sole canonical history; upcast results are replaceable derived state.

`EventUpcasterRegistry` accepts only unique adjacent `n -> n+1` transforms. The evolution handler
walks every step, records input/output digests and stable upcaster identity, and rejects incomplete
chains. JSON is strict UTF-8, duplicate-free, finite, bounded, canonical, and object-shaped. Fields a
revision does not declare as known are treated as opaque extensions and must survive every step with
the same JSON value. A transform that loses an extension, emits invalid data, or changes identity is
quarantined rather than projected.

Unknown majors, future revisions, missing transforms, invalid transforms, and extension loss produce
closed content-free quarantine reasons. They never create a current view. Current documents round-trip
canonically without a transform. Supported older documents produce a deterministic final byte string
and complete adjacent trace; replaying the same source through the same registry is byte-equivalent.

## Persistence, encryption, and resume safety

`event_schema_sources` references the original AgentEvent and authenticates its existing canonical
envelope digest. `SqliteCanonicalEventSourceReader` loads the exact envelope, resolves its Brain key,
verifies key identity/AAD/ciphertext, and returns bytes only to the bounded application pipeline.
Neither migration nor upcasting writes plaintext event documents to SQLite.

`event_schema_views` stores the derived digest/trace and a fresh random AES-256-GCM data-key envelope
wrapped by the existing Brain key hierarchy. `event_schema_quarantine` stores only schema coordinates,
digest, closed reason, and time. A view/quarantine insert and its cursor/counters commit in one
`BEGIN IMMEDIATE` transaction. Duplicate processing is idempotent; cursor regression or target reuse
is a conflict.

Each operation captures a maximum source event ID and total count, so events arriving later cannot
move its goalposts. It processes ordered bounded pages and checkpoints after every outcome. An
exception transitions the run to `interrupted` without removing committed views. Re-execution with
the same operation/target changes it to `running` and continues strictly after the cursor. Completion
is database-constrained to `scanned = total`. The progress query returns only state, target, cursor,
and counters.

## Clean Architecture and compatibility CI

- `ingestion.domain.schema_evolution` owns schema coordinates, strict canonical documents, immutable
  sources, adjacent trace evidence, quarantine outcomes, and progress invariants.
- `ingestion.application.schema_evolution` owns the transform protocol/registry, evolution handler,
  resumable migration use case, and content-free progress query.
- `CanonicalEventSourceReader` and `EventSchemaMigrationRepository` isolate decryption and durable
  state behind narrow ports.
- `sqlite_schema_evolution` is the only SQL/envelope adapter; capture performs only the atomic lineage
  insertion.
- The checked manifest verifier proves every advertised producer revision reaches the current
  revision through adjacent edges and that the current revision has an advertised consumer. Duplicate
  keys, unknown manifest fields, leaps, missing edges, duplicate contracts, and noncanonical versions
  fail CI.

These dependencies keep domain/application code independent of SQLAlchemy, cryptography, filesystem,
HTTP, and composition. Registry extension is Open/Closed; each transform has one responsibility; the
repository and reader ports apply Interface Segregation and Dependency Inversion.

## Migration and rollback

Migration `0014_ing006_schema_evolution` creates constrained source, run, encrypted-view, and
quarantine tables and backfills schema-v1 lineage from existing canonical envelopes. Downgrade is
allowed only when all four tables are empty. Once lineage, progress, views, or quarantine evidence
exists, rollback refuses because deleting it would make upgrade behavior and derived state
unverifiable.
