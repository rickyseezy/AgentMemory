PRO-003 makes a live, content-validated probe—not a manifest declaration—the activation authority for
an embedding or reranking profile. The adapter manifest is still required for supply-chain identity,
limits, protocol compatibility, and declared purposes, but it cannot by itself produce an active
profile.

## Clean Architecture boundaries

- `ProviderProbeSuite`, `VectorValidator`, canaries, untrusted result batches, validated batch facts,
  and suite facts are framework-free domain types.
- `ProbeProviderHandler` reauthorizes the request, verifies the optimistic profile precondition,
  revalidates the exact installed manifest, invokes the provider port, requires the current suite and
  canary identities, constructs immutable evidence, performs domain activation validation, and only
  then asks the repository to commit.
- Built-in wire adapters translate vendor responses into untrusted `EmbeddingProbeBatch` or
  `RerankingProbeBatch` values. They cannot construct durable capability evidence.
- The Qwen bridge performs real embedding or reranking inference against its release-verified local
  sidecar and submits the raw ordered results to the same domain validator.
- Remote adapters receive no credential value. They send credential and destination-policy references
  to the authenticated internal gateway, which enforces the destination and returns model-revision,
  endpoint, and cancellation evidence.
- SQLite is an outbound adapter. It stores the profile revision, probe evidence, normalized capability
  attestation, command operation, audit fact, and outbox event in the same transaction.

These boundaries keep vendor parsing, HTTP, sidecar inference, SQL, and FastAPI out of the domain and
application policy.

## Probe contract

The suite version is `agentmemory.provider-capability-probe.v1`. It uses two fixed, ordered,
non-sensitive canaries with SHA-256 content identities. Content identity includes suite version,
ordinal, and content, so duplicate text still has two distinct IDs. Each configured canonical purpose
must execute exactly once:

- embedding profiles embed the two canaries for every configured purpose;
- reranking profiles rank the two canaries against the fixed non-sensitive probe query;
- the returned purpose set must exactly equal the immutable profile purpose set; and
- every call must report cancellation support and the same model revision, revision fingerprint, and
  endpoint fingerprint.

`VectorValidator` rejects the batch unless all of the following hold:

1. operation and batch type agree;
2. result count and ordered content IDs exactly equal the request;
3. content IDs are unique even when content is duplicated;
4. embedding rows have one exact dimension between 1 and 65,536;
5. every embedding scalar is a Python float, finite, and has absolute value no greater than 1,000,000;
6. every vector has a finite non-zero norm and an L2-declared vector is unit length within `1e-4`;
7. dtype is exactly `float32`;
8. reranking returns one unique permutation of the requested IDs with one finite bounded float score
   per ID; and
9. the validated dimension remains identical across purposes.

The validator hashes canonical float hexadecimal encodings, ordered IDs, purpose, operation, dtype,
normalization, and dimensions. The aggregate validation digest additionally binds every batch digest,
the suite digest, canary digest, exact operation, and ordered purpose set. Raw vectors, scores, canary
content, provider bodies, and credentials are not persisted or returned by the API.

## Immutable capability attestation

`ProviderProbeBinding` binds the profile ID, manifest digest, installed adapter implementation digest,
and immutable configuration digest. `ProviderProbeEvidence` additionally binds:

- gateway-attested endpoint fingerprint;
- exact model ID, immutable model revision, and revision fingerprint;
- operation and exact canonical purpose set;
- dimension, dtype, normalization, similarity, and supported batch ceiling;
- suite, canary, per-batch aggregate validation identities and validated batch count;
- verified cancellation behavior; and
- the UTC probe instant.

Canonical length-framed JSON is SHA-256 content-addressed as `evidence_id`. Reconstructing persistence
recomputes that ID and compares every normalized attestation column to the canonical evidence. The
attestation table has database constraints plus update/delete denial triggers. Changing configuration,
adapter implementation, endpoint, model revision, canaries, validator contract, result facts, or probe
time therefore produces a different evidence identity or fails validation.

An active profile requires evidence whose profile, manifest, configuration, adapter/model/operation,
exact purpose set, limits, and timestamps match the profile. A prior active profile may be refreshed
only without an unexplained revision-fingerprint change; drift is a typed conflict rather than a
silent embedding-space mutation.

## Upgrade and failure behavior

Evidence created before PRO-003 has no runtime-validation attestation and is never upgraded by
inventing facts. Repository reads expose such a profile as `reprobe_required`, omit `active_probe`, and
permit an authorized administrator to run the current suite against the unchanged immutable
configuration. The successful replacement is schema version 2 and returns the profile to `active`.
Missing attestation data for schema-version-2 evidence is treated as integrity failure, not as a
legacy profile.

Vendor authentication, permission, missing-model, rate, timeout, cancellation, response-size,
transient-upstream, model-drift, dimension, malformed-response, privacy, and invalid-configuration
failures map to closed safe error codes. No failed probe reaches `repository.activate`; no capability
attestation, profile revision, audit fact, outbox event, or vector write is committed.

## Test and release evidence

PRO-003 tests cover every specified adversarial class: count, order, duplicate content, duplicate or
unknown IDs, dimension changes, non-float values, NaN, Infinity, zero and huge vectors, normalization,
reranking permutations and scores, malformed JSON/provider shapes, timeout status, missing
cancellation, false or partial purpose support, endpoint/model drift, suite substitution,
configuration/time invalidation, normalized-column tampering, immutable SQL triggers, migration
round-trip, legacy re-probe, and schema-v2 attestation loss.

TDD is mandatory for this story. Release promotion additionally requires the repository linters,
format checks, strict type checks, architecture tests, full test suite, at least 80% line and branch
coverage, at least 80% changed-code coverage, at least 80% mutation score for changed critical code,
dependency/security checks, and the hosted product-quality workflow.

The final local qualification run passed 2,736 tests with only the explicitly unconfigured live
Neo4j integration skipped. Aggregate coverage was 88.24%; the independent policy verifier measured
AgentMemory at 89.63% lines and 82.14% branches, with 89.20% changed lines and 81.82% changed
branches. The complete critical-code mutation campaign generated 11,813 mutants and the independent
verifier accepted 9,539 killed/timeout outcomes for an 80.75% score, above the mandatory 80%
threshold. Hosted workflow evidence remains authoritative after push.
