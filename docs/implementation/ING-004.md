ING-004 protects canonical durability and interactive responsiveness without inventing a second work
ledger. It extends the existing `jobs` table with a closed priority class, typed failure state, and
parent lineage. Scheduler-owned jobs receive a separate mandatory `job_authorizations` row. Existing
PF-001 readiness jobs remain in the same ledger but are not accidentally dispatched by the ING-004
worker because they have no scheduler authorization record.

## Clean Architecture boundaries

- `ingestion.domain.backpressure` owns immutable capacity facts, priority/state/error enums,
  reservation arithmetic, the persisted weighted-fair selection algorithm, complete retry rules,
  strict job records, immutable dead letters, and replay request identity.
- `ingestion.domain.ports` owns scheduler repository, current-grant access, execution registry, and
  local-storage capacity contracts. Application/domain code imports no SQL, FastAPI, disk, or Docker
  implementation.
- `ingestion.application.backpressure` owns authorization order, status/list/replay use cases, worker
  recovery and failure containment, typed retry decisions, and kind-to-executor routing.
- `SqliteJobSchedulerRepository` owns serialized admission, idempotency, persisted fairness cursor,
  lease compare-and-swap, retry scheduling, terminal DLQ transactions, immutable replay receipts,
  threshold alerts, and expired-lease recovery.
- `SqliteCaptureCapacityEnforcer` executes inside the existing `BEGIN IMMEDIATE` AgentEvent append
  transaction. Capacity observation and a new event write therefore cannot race another local writer.
- `backpressure_http_api` is a strict authenticated transport adapter. It exposes no actor/grant,
  input reference, lease owner, arbitrary exception, payload, path, prompt, or provider response.

These boundaries preserve Repository Pattern and dependency inversion: handlers depend on narrow
ports, SQLite and filesystem details remain outbound adapters, and the composition root is the only
place concrete implementations are selected.

## Admission and reservations

`QueueLimits` is immutable and validates monotonic queue/disk thresholds before runtime composition.
Every capacity snapshot contains independently classified pending counts, current free bytes, and an
exact-identity bit. Pending capture includes both priority-class capture jobs and durable unprocessed
AgentEvent outbox work.

Admission is deterministic:

1. An exact existing immutable identity is admitted first, even below the disk hard limit. This lets
   a caller recover an ACK or receive the existing conflict result without rewriting acknowledged
   history.
2. Free bytes at or below the hard threshold reject new work with typed
   `IngestionCapacityError(disk_hard_limit)` before a canonical write.
3. Interactive work may use the full hard queue. Capture cannot consume the interactive reservation.
   Standard/background work can consume neither the interactive nor capture reservation.
4. At the queue or disk soft threshold, new background work is admitted with a durable one-second
   `next_attempt_at` delay. Capture and interactive work remain immediately runnable.
5. Queue thresholds append content-free, unique alert evidence as they are crossed. Alert records
   contain only metric, threshold, observed count/bytes, configured limit, and time.

Production defaults are strict `CoreSettings` values and can be changed only through validated local
configuration. `QueueLimits` rejects a hard limit below soft, overlapping/exhausting reservations,
nonmonotonic disk bounds, an unbounded background stride, or malformed alert percentages.

## Priority, fairness, and leases

The scheduler uses four logically separate priority queues over one normalized ledger:
`interactive`, `capture`, `standard`, and `background`. Due jobs are selected only from scheduler-owned
authorization rows. Within a class, order is stable by `next_attempt_at`, creation time, and job ID.

Normal dispatch persists this weighted cycle:

`interactive, capture, interactive, standard, capture, interactive, standard, background`

Under soft pressure, background is selected exactly once per configured stride while the foreground
cycle continues. Empty queues are skipped without resetting `scheduler_state.dispatch_cursor`.
Consequently an available class cannot starve, worker restarts cannot reset fairness in favor of one
class, and interactive/capture receive intentional service weight.

Claim increments the completed-attempt number and atomically binds owner plus lease deadline. Success
and failure require exact job, state, owner, lease deadline, and attempt count. A stale worker cannot
complete or dead-letter work after lease loss. Startup recovery changes expired authorized leases to
`retry_scheduled` with `transient_storage`, clears the lease, and retains attempt history.

## Retry and poison handling

`RetryPolicy.default()` is a complete mapping for every closed `JobErrorCode`:

- invalid input, authorization denial, integrity violation, and poison input never retry;
- rate limiting retries five attempts with a fixed five-second delay;
- capacity exhaustion retries twelve attempts with a fixed thirty-second delay;
- unavailable dependencies and transient storage retry nine attempts with exponential delay capped at
  sixty seconds; and
- unexpected internal errors retry three attempts with exponential delay capped at four seconds.

Adapters raise `ScheduledJobExecutionError` with only a typed error and safe diagnostic code. Unknown
exceptions become `internal_error/unexpected_worker_failure`; the arbitrary exception string is never
persisted. An unregistered job kind becomes `poison_job/unsupported_job_kind`. The worker contains
executor, repository, and recovery failures so one poison job or temporary store error does not stop
later queues.

When retry is forbidden or exhausted, one transaction changes the job to `dead_lettered`, releases
the exact lease, and appends a unique immutable `dead_letters` row. The record contains identifiers,
priority/kind, request digest, attempt count, typed error/diagnostic codes, and timestamps only.

## Authorized immutable replay

`ReplayDeadLetterHandler` first loads the immutable failure to discover its canonical Brain, then
authorizes the supplied actor/grant against the current active principal, Brain, owner role, and grant
validity. A revoked, expired, wrong-Brain, or wrong-principal grant cannot list or replay failures.

Replay never updates the original job or dead letter. It creates:

- a new UUIDv7 job with corrected request digest and optional content-addressed local input reference;
- `parent_job_id` pointing to the original failed job;
- a new current `job_authorizations` row; and
- an immutable `dead_letter_replays` receipt binding operation, source DLQ, new job, current actor/grant,
  complete replay-request digest, and timestamp.

Exact operation replay returns the same new job. Reusing an operation with different corrected input
is a conflict. Capacity reservations apply to replay just like any new work.

## HTTP and local runtime composition

The production Core starts the scheduler worker alongside projection, durable-ingestion, and ordered
replay workers. The same state-volume disk probe and validated limits are injected into job admission
and canonical AgentEvent capture. Runtime routes are:

- `GET /v1/scheduler/jobs/{job_id}` — currently authorized, content-free job status;
- `GET /v1/dead-letters` — bounded newest-first failure evidence for an exact actor/grant/Brain; and
- `POST /v1/dead-letters/{dead_letter_id}:replay` — `Idempotency-Key`-bound corrected replay.

Installation bearer authentication occurs before application handlers. Scope authorization then runs
inside the use case. Capacity maps to HTTP 507 with `AM_CAPACITY_EXHAUSTED` and `retryable=true`; the
internal threshold reason is not exposed. Batch capture classifies capacity as retryable per item.

The OpenAPI exporter includes side-effect-free contract routers and remains byte deterministic.
